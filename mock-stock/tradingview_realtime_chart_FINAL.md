# TradingView Lightweight Charts 실시간 주가 차트 최종 명세

## 1. 문서 목적

본 문서는 증권사 API에서 과거 OHLCV와 실시간 체결 데이터를 받아 웹 또는 앱의 종목 상세 화면에 실시간 차트를 표시하기 위한 최종 개발 명세다.

차트 렌더링에는 **TradingView Lightweight Charts**를 사용한다. TradingView에서 시세를 가져오는 구조가 아니라, 증권사에서 받은 데이터를 자체 Backend와 Frontend를 거쳐 Lightweight Charts에 입력하는 구조다.

## 2. 최종 아키텍처

```text
┌──────────────────────────────┐
│          증권사 API          │
│                              │
│ REST: 과거 OHLCV             │
│ WebSocket: 실시간 체결       │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│           Backend            │
│                              │
│ 인증 토큰 및 접속키 관리     │
│ 종목코드 매핑                │
│ 데이터 정규화                │
│ 체결 → 현재 봉 집계          │
│ REST 및 WebSocket 제공       │
└──────────────┬───────────────┘
               │
       ┌───────┴────────┐
       │                │
       ▼                ▼
과거 데이터 REST    실시간 WebSocket
       │                │
       └───────┬────────┘
               ▼
┌──────────────────────────────┐
│           Frontend           │
│                              │
│ 최초 과거 봉 로딩            │
│ 실시간 메시지 구독           │
│ 선/캔들 차트 전환            │
│ 연결 복구 및 상태 표시       │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ TradingView Lightweight      │
│ Charts                       │
│                              │
│ Candlestick Series           │
│ Line Series                  │
└──────────────────────────────┘
```

### 핵심 원칙

1. 시세 데이터 원천은 증권사 API다.
2. 증권사 인증정보와 접속키는 Backend에서만 관리한다.
3. Frontend는 증권사 API에 직접 접속하지 않는다.
4. 과거 봉은 REST로 최초 로딩한다.
5. 실시간 체결 및 현재 봉 업데이트는 WebSocket으로 전달한다.
6. Lightweight Charts는 데이터 공급자가 아니라 화면 렌더링 라이브러리로만 사용한다.
7. Supabase는 실시간 시세 전달 경로에서 제외하되, 일봉 1년치와 주봉 3년치의 과거 OHLCV 캐시로 사용한다.

## 3. 구성 요소별 책임

### 3.1 증권사 API

증권사 API는 다음 데이터를 제공해야 한다.

- 과거 OHLCV: 시간, 시가, 고가, 저가, 종가, 거래량
- 실시간 체결: 종목코드, 체결시간, 체결가, 체결수량
- 선택 항목: 전일 종가, 등락률, 누적 거래량, 장 운영 상태

필수 확인 사항:

- REST 및 WebSocket 호출 제한
- 동시 구독 가능 종목 수
- 토큰 및 접속키 만료 정책
- 재접속 및 구독 복구 방식
- 장중/장외/동시호가 데이터 구분
- 상업적 이용 및 시세 재배포 허용 범위

### 3.2 Backend

Backend의 역할은 다음과 같다.

- 증권사 인증 토큰 발급 및 갱신
- 증권사 WebSocket 연결 유지
- 종목별 구독 등록 및 해제
- 증권사별 데이터 형식을 서비스 표준 형식으로 변환
- 실시간 체결을 타임프레임별 OHLCV 봉으로 집계
- 과거 OHLCV 조회용 REST API 제공
- 실시간 체결/봉 전송용 WebSocket 제공
- 중복 체결, 역순 메시지 및 비정상 값 방어
- 접속 종료 시 재연결 및 구독 복원

Backend는 여러 Frontend 사용자가 같은 종목을 보고 있을 때 증권사 구독을 사용자마다 새로 만들지 않는다. 종목별 단일 upstream 구독을 공유하고, 필요한 사용자에게 fan-out하는 구조를 권장한다.

### 3.3 Frontend

Frontend의 역할은 다음과 같다.

- 화면 진입 시 과거 OHLCV REST 요청
- Lightweight Charts 인스턴스 생성
- 기본 차트 유형 표시
- Backend WebSocket 연결 및 종목 구독
- 실시간 현재 봉 업데이트
- 선차트/캔들차트 전환
- 종목 및 타임프레임 변경 시 기존 구독 해제
- 연결 끊김, 재연결 중, 장 마감 등의 상태 표시

### 3.4 TradingView Lightweight Charts

Lightweight Charts는 다음 용도로만 사용한다.

- Candlestick Series를 통한 캔들차트 렌더링
- Line Series를 통한 선차트 렌더링
- 시간축, 가격축, 크로스헤어 및 반응형 레이아웃 제공
- 신규 봉 또는 현재 봉을 `update()` 방식으로 반영

TradingView 서버에 시세를 전송하거나 TradingView에서 시세를 조회하지 않는다.

## 4. 데이터 흐름

### 4.1 종목 화면 최초 진입

1. Frontend가 종목코드와 타임프레임을 기준으로 Backend REST API를 호출한다.
2. Backend가 캐시 또는 증권사 REST API에서 과거 OHLCV를 조회한다.
3. Backend가 데이터를 표준 형식으로 정규화해 반환한다.
4. Frontend가 캔들 시리즈 또는 라인 시리즈에 과거 데이터를 일괄 설정한다.
5. Frontend가 Backend WebSocket에 연결하고 해당 종목을 구독한다.
6. Backend가 새로운 체결 또는 갱신된 현재 봉을 실시간으로 전송한다.
7. Frontend가 마지막 봉을 갱신하거나 새 봉을 추가한다.

### 4.2 실시간 체결 처리

```text
증권사 실시간 체결
        ↓
Backend 수신 및 검증
        ↓
해당 타임프레임의 봉 구간 계산
        ↓
현재 봉 OHLCV 갱신 또는 신규 봉 생성
        ↓
Frontend WebSocket으로 전송
        ↓
Lightweight Charts series.update()
```

1분봉 집계 예시:

```text
10:01:00  94,000원 → open/high/low/close = 94,000
10:01:15  94,300원 → high = 94,300, close = 94,300
10:01:31  93,900원 → low = 93,900, close = 93,900
10:01:59  94,200원 → close = 94,200
10:02:00  새 체결  → 10:02 봉 신규 생성
```

## 5. API 명세

### 5.1 과거 OHLCV REST API

```http
GET /api/v1/market-data/{symbol}/bars?timeframe=1m&from=...&to=...&limit=500
```

응답 예시:

```json
{
  "symbol": "005930",
  "timeframe": "1m",
  "timezone": "Asia/Seoul",
  "bars": [
    {
      "time": 1786492860,
      "open": 94000,
      "high": 94300,
      "low": 93900,
      "close": 94200,
      "volume": 18235
    }
  ],
  "hasMore": true
}
```

규칙:

- `time`은 초 단위 Unix timestamp로 통일한다.
- 데이터는 시간 오름차순으로 반환한다.
- 같은 `time`의 봉은 하나만 존재해야 한다.
- 가격 및 거래량은 가능한 한 숫자형으로 반환한다.
- 거래소 시간대와 세션 규칙은 Backend에서 일관되게 적용한다.

### 5.2 Frontend WebSocket

연결 예시:

```text
wss://api.example.com/ws/market-data
```

구독 요청:

```json
{
  "type": "subscribe",
  "symbol": "005930",
  "timeframe": "1m"
}
```

구독 해제:

```json
{
  "type": "unsubscribe",
  "symbol": "005930",
  "timeframe": "1m"
}
```

봉 업데이트 메시지:

```json
{
  "type": "bar",
  "symbol": "005930",
  "timeframe": "1m",
  "data": {
    "time": 1786492860,
    "open": 94000,
    "high": 94300,
    "low": 93900,
    "close": 94200,
    "volume": 18235
  }
}
```

선택적으로 원시 체결 메시지를 제공할 수 있다.

```json
{
  "type": "trade",
  "symbol": "005930",
  "data": {
    "time": 1786492919,
    "price": 94200,
    "quantity": 10,
    "sequence": 3817291
  }
}
```

연결 상태 메시지 예시:

```json
{
  "type": "status",
  "status": "connected",
  "market": "KRX",
  "serverTime": 1786492920
}
```

## 6. 선차트와 캔들차트 전환

Frontend는 사용자에게 다음 두 가지 차트 유형만 제공한다.

- 선차트: 각 봉의 `close`만 사용
- 캔들차트: `open`, `high`, `low`, `close` 사용

같은 OHLCV 원본을 사용하므로 차트 유형을 바꿀 때 Backend 데이터를 다시 요청할 필요가 없다.

```text
OHLCV 원본
   ├─ Candlestick Series: open/high/low/close
   └─ Line Series: close
```

권장 구현 방식:

1. Frontend 상태에 현재 차트 유형을 `line` 또는 `candlestick`으로 저장한다.
2. 과거 OHLCV 원본은 메모리에 유지한다.
3. 전환 시 기존 시리즈를 제거하고 선택한 시리즈를 생성한다.
4. 캔들차트에는 OHLC를 그대로 설정한다.
5. 선차트에는 `{ time, value: close }` 형태로 변환해 설정한다.
6. WebSocket 메시지는 같은 OHLCV 원본 상태를 갱신한 뒤 현재 시리즈 형식에 맞게 반영한다.

초보자 중심 서비스라면 기본값은 선차트를 권장한다.

## 7. 실시간 봉 집계 규칙

Backend가 체결 데이터로 봉을 생성하는 경우 아래 규칙을 사용한다.

- `open`: 해당 구간의 첫 체결가
- `high`: 해당 구간 체결가 중 최고가
- `low`: 해당 구간 체결가 중 최저가
- `close`: 해당 구간의 최신 체결가
- `volume`: 해당 구간 체결수량 합계

추가 처리 원칙:

- 봉 시작 시각은 타임프레임 경계로 내림 처리한다.
- 같은 봉 구간의 체결은 마지막 봉을 갱신한다.
- 다음 구간 체결이 들어오면 새 봉을 생성한다.
- 중복 메시지는 체결번호 또는 sequence를 기준으로 제거한다.
- 지연 도착한 체결의 허용 범위를 정하고, 필요하면 해당 과거 봉을 보정한다.
- 장 마감 후 확정 봉과 실시간 임시 봉을 구분할 수 있어야 한다.
- 수정주가 적용 여부와 기준을 과거/실시간 데이터에서 일치시킨다.

## 8. Supabase 사용 범위

Supabase는 다음 실시간 경로에 포함하지 않는다.

```text
증권사 WebSocket → Backend → Frontend WebSocket → Lightweight Charts
```

즉 실시간 체결마다 다음 경로를 거치지 않는다.

```text
증권사 → Backend → Supabase → Frontend
```

실시간 경로에서 제외하는 이유:

- 불필요한 지연 감소
- 체결량 증가 시 DB 쓰기 및 Realtime 이벤트 비용 방지
- 동일 체결의 중복 저장 및 중복 전달 위험 감소
- 연결 장애 구간과 책임 범위 단순화

Supabase는 다음 용도로 사용한다.

- 사용자 계정 및 인증
- 관심종목
- 모의투자 주문, 체결 및 잔고
- 사용자 설정과 기본 차트 유형
- 서비스 운영용 메타데이터
- 분석 또는 복구가 필요한 집계 이력
- `stock_candles`의 일봉 최근 1년치와 주봉 최근 3년치

차트 요청 시 Backend는 일봉·주봉의 DB 최신 시각을 확인하고 증권사 REST API에서 그 이후 구간을 조회해 upsert한다. 같은 동기화에서 일봉 1년, 주봉 3년보다 오래된 행은 삭제해 보관량을 일정 범위로 유지한다. 분봉은 저장하지 않고 증권사 REST API에서 최근 2주치를 페이지 끝까지 조회한다.

## 9. 연결 및 장애 처리

### Backend와 증권사 연결

- 끊김 감지 후 지수 백오프로 재연결한다.
- 재연결 성공 시 기존 종목 구독을 자동 복구한다.
- 누락 가능 구간은 증권사 REST API로 다시 조회해 보정한다.
- 인증 토큰 또는 접속키 만료 전에 안전하게 갱신한다.

### Frontend와 Backend 연결

- ping/pong 또는 heartbeat로 연결 상태를 확인한다.
- 끊김 시 자동 재연결한다.
- 재연결 후 현재 종목과 타임프레임을 다시 구독한다.
- 재연결 직후 최근 봉을 REST로 재조회하여 누락 또는 불일치를 보정한다.
- 화면에는 `실시간`, `재연결 중`, `지연`, `장 마감` 상태를 구분해 표시한다.

## 10. 성능 및 확장

- 종목별 증권사 upstream 구독은 Backend에서 공유한다.
- 사용자별 연결은 Backend가 fan-out한다.
- 최근 과거 봉은 메모리 또는 Redis 캐시 사용을 검토한다.
- WebSocket 메시지는 변경된 마지막 봉만 전송한다.
- 화면 밖 종목 또는 사용자가 이탈한 종목은 구독 참조 수가 0이 되면 해제한다.
- 서버 인스턴스가 여러 개인 경우 구독 소유권과 메시지 브로커 구조를 명시한다.
- 사용자별 WebSocket 연결 수, 메시지 빈도 및 종목 구독 수를 제한한다.

## 11. 보안

- 증권사 API Key, Secret, 계좌정보 및 접속키를 Frontend에 노출하지 않는다.
- 모든 외부 통신은 HTTPS/WSS를 사용한다.
- Frontend WebSocket 연결에 사용자 인증과 권한 검사를 적용한다.
- 구독 가능한 종목과 요청 빈도를 검증한다.
- 입력 종목코드, 타임프레임 및 조회 범위를 화이트리스트로 제한한다.
- 비밀값은 환경변수 또는 비밀관리 시스템에 보관한다.
- 로그에 API Secret, 토큰 및 개인정보를 남기지 않는다.

## 12. 라이선스 및 운영 전 확인

기술적으로 연결 가능하더라도 증권사 및 거래소의 시세 이용 조건을 별도로 확인해야 한다.

- 개인 조회용 API 데이터를 다수 사용자에게 재배포할 수 있는지
- 실시간 시세의 상업적 이용이 허용되는지
- 지연 시세 표시 또는 출처 표기가 필요한지
- 저장 가능한 데이터 범위와 보존 기간
- 동시 접속자 및 종목 구독 제한
- TradingView Lightweight Charts의 라이선스와 출처표시 조건

서비스 출시 전에는 증권사 및 거래소와 시세 재배포 권한을 서면으로 확인하는 것을 권장한다.

## 13. 권장 MVP 범위

1차 MVP는 다음 범위로 제한한다.

- 지원 종목: 서비스 대상 종목 목록
- 타임프레임: 1분봉 및 일봉
- 차트 유형: 선차트, 캔들차트
- 과거 데이터: REST 최초 로딩
- 실시간 데이터: WebSocket 현재 봉 업데이트
- 기본 차트: 선차트
- 재연결 및 최근 봉 재동기화
- Supabase는 사용자/모의투자 데이터와 일봉 1년·주봉 3년 캐시에 사용

거래량 차트, 보조지표, 드로잉 도구, 다중 패널 등은 MVP 이후 별도 기능으로 검토한다.

## 14. 완료 조건

다음 조건을 모두 만족하면 구현 완료로 본다.

- 종목 화면 진입 시 과거 OHLCV가 정상 표시된다.
- 새로운 체결이 들어오면 현재 봉이 실시간으로 갱신된다.
- 봉 경계가 바뀌면 새 봉이 추가된다.
- 선차트와 캔들차트 전환 시 추가 API 호출 없이 동일 데이터가 표시된다.
- 종목 및 타임프레임 변경 시 이전 구독이 정상 해제된다.
- 일시적인 연결 끊김 이후 자동 재연결 및 데이터 보정이 된다.
- 실시간 시세 경로가 Supabase를 거치지 않는다.
- 증권사 인증정보가 Frontend와 사용자에게 노출되지 않는다.
- 시세 이용 및 재배포 조건이 확인되어 있다.

## 15. 최종 결론

최종 구조는 다음과 같다.

```text
과거 데이터:
증권사 REST API → Backend REST API → Frontend → Lightweight Charts

실시간 데이터:
증권사 WebSocket → Backend → Frontend WebSocket → Lightweight Charts

차트 전환:
동일 OHLCV → 캔들차트는 OHLC 사용 / 선차트는 close 사용

Supabase:
사용자·주문·설정·선택적 집계 저장에 사용
실시간 시세 전달 경로에서는 제외
```

Backend가 받은 데이터를 TradingView로 직접 보내는 것이 아니라, **Backend가 Frontend에 데이터를 제공하고 Frontend에서 실행되는 TradingView Lightweight Charts가 이를 렌더링한다.** 이것이 본 서비스의 최종 실시간 차트 구조다.
