# 팀 병렬 Git 정책

## 역할

| 이름 | 트랙 | 역할 |
|---|---|---|
| **이재용** | 전략시뮬게임 | **통합 오너** — 공유 핫스팟 단일 작성자 지정, PR 머지 승인, 루트 진입점 문서 |
| 이호연 | 전략시뮬게임 | 룰 엔진·게임 UI |
| 박혜준 | 뉴스 | 아이 눈높이 뉴스 |
| 강소정 | 뉴스 | 아이 눈높이 뉴스 |
| **김설빈** | 실제투자 | **팀장** — 팀 운영·일정·범위 조율 |
| 김경렬 | 실제투자 | 제안·승인·체결 |

- git-coordinator: 세션·브랜치·워크트리 생성과 상태 등록을 직렬화.
- 작업 세션: 할당된 워크트리와 claim 범위만 수정.
- 팀원: 작업 시작 후 첫 커밋에서 Draft PR을 열어 원격 작업 의도를 공개.

팀장(김설빈)과 통합 오너(이재용)는 다른 역할이다. 팀장은 **무엇을 언제 할지**를,
통합 오너는 **누가 공유 파일을 쓸지와 머지 여부**를 정한다.

## 저장소 배치

- 루트 워크트리(`C:\dev\six-opening`): 항상 깨끗한 `main`. 관제·감사·통합 확인 전용이며 코드를 수정하지 않는다.
- 기능 작업: 작업마다 별도 브랜치·워크트리·PR.
- 하나의 브랜치를 여러 PR에 재사용하지 않는다.
- 병합 후 후속 작업은 최신 `origin/main`에서 새 브랜치로 시작한다.

## 브랜치 형식

`<도구>/<작업자>/<작업명>`

- 도구: `codex`, `claude`만 허용한다.
- 작업자: `이재용`, `이호연`, `박혜준`, `강소정`, `김설빈`, `김경렬`만 허용한다.
- 작업명: 영문 소문자 또는 숫자로 시작하고 영문 소문자·숫자·`-_.`만 허용한다.
- `~`는 문서의 생략·예시 표기일 뿐 실제 Git 브랜치에는 사용할 수 없다.
- 브랜치의 도구·작업자와 세션 등록 정보가 다르면 세션 시작과 파일 편집을 차단한다.
- 기존 구형 브랜치는 정리 전용이다. 후속 수정은 최신 `main`에서 새 규칙 브랜치로 옮긴다.

예시:

- `claude/박혜준/kid-news-feed`
- `codex/김경렬/proposal-execute`
- `claude/이호연/t5-difficulty-ui`

## 워크트리 경로

`start`가 자동으로 만든다. 형식은 저장소 루트의 형제 디렉터리다.

```
C:\dev\six-opening-<도구>-<작업자>-<작업명>
```

예: `C:\dev\six-opening-claude-박혜준-kid-news-feed`

이미 존재하는 경로면 세션 생성이 거부된다. 다른 세션의 워크트리에 들어가서 수정하지 않는다.

## 담당 경계 — 폴더가 곧 경계다

| 트랙 | 담당 | 경로 |
|---|---|---|
| ① 전략시뮬게임 | 이재용·이호연 | `game/` 전체 (`game/src` 엔진, `game/ui` 화면) |
| ② 뉴스 | 박혜준·강소정 | `web/app/kid/news`, `web/app/api/news`, `web/lib/news` |
| ③ 실제투자 | 김설빈·김경렬 | `web/app/kid`(news 제외), `web/app/parent`, `web/app/api`(news 제외), `web/lib`(news 제외) |

담당 밖 폴더는 읽기 자유, 수정은 담당자 합의 + PR.

## 공유 핫스팟

다음은 여러 트랙이 함께 쓴다. 동시에 한 명만 수정한다.

- 앱 진입·공통 레이아웃: `web/app/layout.tsx`, `web/app/globals.css`, `web/app/page.tsx`
- 공용 프론트·백엔드 계약: `web/lib/types.ts`
- DB 스키마: `web/lib/db.ts`
- 기획안 조항 검증: `web/scripts/verify.ts`
- 엔진 계약·룰 SSOT: `game/src/types.ts`, `game/src/engine.ts`
- 대형 조립 루트: `game/ui/src/App.tsx`
- 패키지 매니페스트: `web/package.json`, `game/ui/package.json`
- 설계 SSOT: `docs/game-design.md`, `docs/mvp-backlog.md`

`start`·`claim`이 claim 경로 겹침을 검사하므로, 위 파일을 두 세션이 동시에 claim하면
두 번째 세션 생성이 실제로 차단된다. 핫스팟 목록은 "겹쳤을 때 누가 정하는가"의 근거다.

## 통합 오너 전용 파일

아래는 이재용 세션만 수정한다. 다른 팀원의 AI는 어떤 이유로도(동기화 갱신 포함) 건드리지 않는다.

- `AGENTS.md`, `CLAUDE.md`
- `web/AGENTS.md`, `web/CLAUDE.md`
- `game/AGENTS.md`, `game/CLAUDE.md`
- `물려주는계좌_기획안.md`
- `docs/team/_공통_AI규칙.md`
- `scripts/git_session_manager.py`

변경이 필요하면 내용을 정리해 이재용에게 요청한다.

## 충돌 처리

1. 열린 PR과 active claim의 수정 경로를 먼저 비교한다.
2. 겹치지 않으면 병렬 진행한다.
3. 일반 파일이 겹치면 작업 범위를 분할한다.
4. 핫스팟이 겹치면 이재용이 작성자 한 명을 지정한다.
5. 화면 구현자는 신규 파일을 만들고, 공용 라우팅·레이아웃 연결은 통합 오너가 별도 PR로 처리한다.
6. 계약 변경은 계약 → 구현 → 소비자 → 통합 순으로 병합한다.

## PR 규칙

- 첫 의미 있는 커밋 직후 Draft PR을 연다.
- PR base는 항상 `main`이다. 병합된 기능 브랜치를 base로 둔 stacked PR을 만들지 않는다.
- 담당자·작업 범위·공유 핫스팟·계약 변경을 본문에 기록한다.
- Ready 전 최신 `main`을 반영하고 관련 테스트를 실행한다.
- `hotspot-approved` 라벨은 이재용이 GitHub에서 직접 적용해야 유효하다.
- 충돌 해결은 PR 브랜치 소유자 또는 이재용이 담당한다.
- 병합 후 원격 브랜치는 자동 삭제하고 로컬은 정리 절차로 제거한다.
