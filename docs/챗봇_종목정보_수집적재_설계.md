# 챗봇 종목 정보 수집·적재 설계

## 1. 목표

[사실] 키웅이는 모의투자 유니버스의 13개 섹터·51개 종목에 대해 아래 의미의 질문에 답해야 한다.

1. “(종목명)이 뭐 하는 회사야?”
2. “(종목명)은 무엇을 만들어?”
3. “내가 (종목명)을 어디에서 만날 수 있어?”
4. “(섹터명) 섹터는 어떤 일을 해?”

[확정] 답변은 초등학생~중학생이 이해할 수 있는 사실 설명이며, 종목 추천·매매 시점·목표가·수익률 전망·우열 판단을 포함하지 않는다.

## 2. 질문과 데이터의 1:1 연결

질문마다 필요한 사실이 다르므로, 회사 데이터와 섹터 데이터를 한 문장에 섞어 저장하지 않는다.

| 사용자 질문 | 답변에 쓰는 데이터 | 관리 단위 |
|---|---|---|
| “(종목명)이 뭐 하는 회사야?” | 회사 한 줄 소개, 산업 속 역할, 주요 고객 유형 | 종목 51개별 |
| “(종목명)은 무엇을 만들어?” | 대표 제품·서비스 범주, 제공 방식 | 종목 51개별 |
| “내가 (종목명)을 어디에서 만날 수 있어?” | 검증된 일상 접점 1~3개 | 종목 51개별 |
| “(섹터명) 섹터는 어떤 일을 해?” | 산업의 공통 역할, 가치사슬, 쉬운 용어 풀이 | 섹터 13개별 |

예를 들어, ‘반도체 섹터’의 공통 설명은 한 번만 작성하고, 삼성전자·SK하이닉스·LG이노텍은 각자의 회사 역할·제품 범주·일상 접점만 별도로 작성한다.

## 3. 적재할 데이터 세트

### A. 종목 마스터: 식별과 검색

기존 유니버스 설계의 `StockMaster`를 기준으로 한다. 주문, 시세, 챗봇 콘텐츠가 같은 `stockId`를 사용해야 한다.

```ts
type StockMaster = {
  id: string;                 // 내부 불변 식별자, 예: "KRX:종목코드"
  symbol: string;             // 시세 API용 검증된 종목코드
  name: string;               // 공식 화면 표시명
  searchAliases: string[];    // 약칭·띄어쓰기·영문 표기
  sector: SectorKey;          // 13개 고정 키 중 하나
  market: "KOSPI" | "KOSDAQ";
  isActive: boolean;
  displayOrder: number;
};
```

### B. 섹터 교육 데이터: 13개 행

섹터 설명은 모든 종목에 복사하지 않고 한 번만 저장한다.

```ts
type SectorEducation = {
  sector: SectorKey;
  label: string;                 // 화면용 한국어 이름
  elementarySummary: string;     // 초등학생용 1~2문장
  middleSchoolSummary: string;   // 중학생용 2~3문장
  valueChain: string[];          // 쉬운 순서: 만들기 → 전달하기 → 사용하기
  keyTerms: Array<{
    term: string;
    definition: string;
  }>;
  factSources: FactSource[];
};
```

### C. 종목 교육 데이터: 51개 행

네 가지 질문을 모두 답할 수 있게, 종목마다 아래 필드를 필수로 둔다.

```ts
type StockEducation = {
  stockId: string;
  companySummary: string;          // “뭐 하는 회사야?”
  companyRole: string;             // 같은 섹터 안의 역할
  offerings: string[];             // “무엇을 만들어?”의 제품·서비스 범주 2~4개
  everydayTouchpoints: string[];   // “어디에서 만날 수 있어?”의 일상 접점 1~3개
  elementaryExplanation: string;   // 어려운 말을 줄인 1~2문장
  middleSchoolExplanation: string; // 고객·제조·유통 등 연결을 더한 2~3문장
  approvedQuestions: string[];     // 추천 질문 칩 4개 이상
  factSources: FactSource[];
  reviewedAt: string;              // 사실 검수일 ISO 날짜
  status: "draft" | "reviewed";
};

type FactSource = {
  field: "identity" | "business" | "offering" | "touchpoint" | "sector";
  title: string;
  url: string;
  publishedAt?: string;
  checkedAt: string;
};
```

`offerings`에는 제품명 나열 대신 “게임 서비스”, “택배·운송 서비스”, “자동차 부품”처럼 오래 유지되는 **제품·서비스 범주**를 우선 저장한다. 브랜드·작품·특정 계약은 변동 가능성이 커 별도 검수 없이 넣지 않는다.

## 4. 사실 수집 원본의 우선순위

51개 종목은 적은 수이므로, 자동 요약보다 사람이 확인한 출처 기반 수집을 기본으로 한다. 원문 전체를 복사해 저장하기보다, 필요한 사실을 짧게 구조화하고 출처 링크·확인일을 남긴다.

| 우선순위 | 원본 | 사용할 정보 | 용도 |
|---:|---|---|---|
| 1 | 거래소 상장정보 | 종목코드, 공식 종목명, 시장구분 | `StockMaster` 식별 검증 |
| 2 | 전자공시의 회사 개황·사업 내용 | 회사의 주요 사업과 사업 부문 | 회사 한 줄 소개·산업 역할 |
| 3 | 회사 공식 홈페이지·IR | 제품·서비스 범주, 사업 소개 | `offerings`, `companyRole` |
| 4 | 회사의 공식 브랜드·서비스 페이지 | 실제 사용자가 만나는 제품·서비스 접점 | `everydayTouchpoints` |
| 5 | 공공기관·산업 협회 교육 자료 | 섹터의 기본 구조와 용어 | `SectorEducation` |

뉴스 기사, 블로그, 위키, 검색 결과 요약은 초안 탐색에는 사용할 수 있지만 최종 챗봇 사실 원본으로 단독 채택하지 않는다. 실적·주가·계약·점유율처럼 기준일이 중요한 정보는 이 네 질문의 기본 데이터에 넣지 않는다.

## 5. 수집·검수·적재 절차

### 단계 1 — 51개 작업 목록을 만든다

`universe.csv` 또는 시트에 아래 열을 먼저 만든다. 이 단계에서는 회사 설명을 쓰지 않는다.

```text
stockId, name, sector, officialName, symbol, market, owner, status
```

- `name`, `sector`는 확정 유니버스와 반드시 일치해야 한다.
- `symbol`, `market`은 거래소 상장정보로 확인 전까지 비워 둔다.
- `owner`는 콘텐츠 조사 담당자, `status`는 `todo → sourced → drafted → reviewed → loaded` 순서로 관리한다.

### 단계 2 — 출처 카드로 사실을 모은다

종목 하나당 아래 네 가지 사실을 각각 최소 한 개의 원본으로 확인한다.

```text
1. 회사가 하는 일: 사업 내용 또는 회사 소개
2. 제품·서비스 범주: 공식 사업·제품 페이지
3. 일상 접점: 실제로 이용자에게 닿는 공식 제품·서비스 페이지
4. 산업 속 역할: 섹터 설명과 사업 내용의 연결
```

조사 노트에는 “원문 문장” 대신 **검증된 사실의 짧은 메모 + URL + 확인일**을 남긴다. 예를 들어 “택배 서비스를 제공한다”처럼 사실만 적고, “성장성이 좋다” 같은 해석은 적지 않는다.

### 단계 3 — 청소년용 문장으로 편집한다

각 사실 메모를 초등학생용과 중학생용으로 나눈다.

| 수준 | 작성 규칙 |
|---|---|
| 초등학생용 | 1~2문장, 한 문장에 한 개념, 친숙한 예시 사용, 전문용어는 바로 풀이 |
| 중학생용 | 2~3문장, 고객·제조·유통·서비스의 연결을 설명, 수익·전망 판단은 제외 |

다음 단어는 아이가 이해할 수 있는 말로 풀어 쓴다.

| 원어 | 쉬운 설명 예시 |
|---|---|
| 플랫폼 | 여러 사람이 서비스를 이용하도록 연결해 주는 장소나 앱 |
| 물류 | 물건을 필요한 곳까지 옮기고 전달하는 일 |
| 반도체 | 휴대폰·컴퓨터 같은 전자기기 안에서 일을 처리하게 돕는 작은 부품 |
| 중개 | 두 사람이 직접 만나지 않아도 거래를 연결해 주는 일 |

### 단계 4 — 자동·사람 검수를 함께 한다

자동 검수는 누락과 구조 오류를, 사람 검수는 사실성·눈높이·안전성을 맡는다.

```text
자동 검수
  - StockMaster 51개와 StockEducation 51개의 stockId가 정확히 1:1인지
  - 13개 SectorEducation이 모두 있는지
  - 필수 필드, 출처 URL, 확인일, reviewedAt이 비어 있지 않은지
  - 금지 표현(매수·매도 권유, 목표가, 손절가, 오를 것, 수익 보장)이 없는지

사람 검수
  - 출처가 해당 필드를 실제로 뒷받침하는지
  - 초등학생이 이해할 수 있는 말인지
  - 제품·브랜드·서비스의 최신성이 확인됐는지
  - 방산·금융·화장품 분야에 과도한 안전·효능·수익 암시가 없는지
```

### 단계 5 — 코드 데이터로 적재한다

검수 완료 행만 정적 TypeScript 데이터로 변환한다.

```text
조사 시트/CSV (작업·검수용)
  → 스키마 검증 스크립트
  → web/shared/data/stocks.ts
  → web/shared/data/sectors.ts
  → web/shared/data/stock-education.ts
  → F2 종목 상세와 F10 챗봇에서 stockId로 조회
```

MVP에서는 정적 데이터가 적합하다. 외부 데이터베이스나 모델 지식에만 의존하지 않아도, 데모 중 사실 설명이 일관되게 동작한다.

## 6. 질문 응답 로직

자연어를 정규화한 뒤, 종목명 또는 `searchAliases`와 질문 의도를 분리한다.

```text
입력: “삼성전자는 무엇을 만들어?”
  → 종목 인식: 삼성전자 → stockId
  → 의도 인식: 무엇을 만들어
  → StockEducation.offerings + elementaryExplanation 반환

입력: “물류 섹터는 어떤 일을 해?”
  → 섹터 인식: 물류 → SectorKey.logistics
  → 의도 인식: 섹터 역할
  → SectorEducation.elementarySummary 또는 middleSchoolSummary 반환
```

우선순위는 **고정 사실 데이터 → 화면 컨텍스트 계산 → OpenAI 폴백**이다. 이 네 가지 질문은 51개 종목·13개 섹터 모두 고정 데이터로 답할 수 있어야 하며, 모델 호출에 의존하지 않는다.

## 7. 갱신 정책

- 종목코드·시장구분: 상장 정보 변경 시 즉시 재검수
- 회사 한 줄 소개·제품/서비스 범주·일상 접점: 분기 1회와 회사 공식 페이지 변경 확인 시 재검수
- 섹터 설명: 산업 구조가 바뀌거나 용어가 어려운 것으로 확인될 때 재검수
- 모든 변경: `reviewedAt`과 해당 `FactSource.checkedAt`을 함께 갱신

## 8. 완료 기준

- 51개 종목 각각에 네 질문을 답할 수 있는 `StockEducation` 행이 있다.
- 13개 섹터 각각에 “어떤 일을 해?”를 답할 수 있는 `SectorEducation` 행이 있다.
- 각 사실 필드에 출처 URL과 확인일이 있으며, 사람 검수를 통과했다.
- 모든 답변은 초등학생용·중학생용 문장을 갖고, 3문장 이내로 표시할 수 있다.
- 고정 사실 질문은 OpenAI 호출 없이 답하며, 생성형 답변이 필요할 때도 `web/shared/llm` 출력 필터를 통과한다.
