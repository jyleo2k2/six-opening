## 2. 실제 런타임 구조

```text
Next.js [[...screen]]
└─ web/app/[[...screen]]/page.tsx   (routeFromPath로 주소 해석 + kw_uid 세션 쿠키 확인)
   ├─ 모르는 주소 → notFound()
   ├─ 비로그인   → LoginGate  (스플래시 + 로그인 폼, SignupWizard 화면)
   └─ 로그인
      ├─ /ranking → RankingScreen  (React가 직접 그린다. app.html 없음)
      └─ 그 밖    → ConnectedPrototype
         ├─ iframe: /ui/app.html?runtime=1
         │  ├─ 홈·탐색·상세·뉴스·매수·매도·포트폴리오·아카이브
         │  └─ iframe: /tradingview-chart (종목 차트 화면에서만)
         └─ F10 ChatbotOverlay
```

F11 가족 기록에는 React 오버레이가 없다. 피드는 `app.html` 아카이브 화면의 **수익률(`return`) 탭** 안에 있다.

**화면 해체가 진행 중이다.** 화면을 하나씩 `app.html`에서 실제 라우트로 옮기고 있고, 지금까지 옮긴 화면은 `/ranking` 하나다(PR #211). 옮긴 화면은 폰 프레임을 `features/f0-home/PhoneFrame`으로 직접 그리며, `app.html`을 iframe으로 띄우지 않는다.

### 2.1 사용자 라우트

주소는 `features/f0-home/screen-route.ts`가 소유한다. `routeFromPath`가 아는 주소만 앱이고, **나머지는 404다**(오타가 조용히 홈으로 넘어가지 않는다).

| 경로 | 현재 역할 | 렌더링 |
|---|---|---|
| `/` | 홈 | `app.html` iframe |
| `/explore` | 51종 종목 탐색 | `app.html` iframe |
| `/ranking` | 가족 리그 순위 | **React `RankingScreen`** |
| `/portfolio` | 보유 자산 | `app.html` iframe |
| `/archive` | 성향·수익률 2탭 | `app.html` iframe |
| `/stock/{6자리코드}` | 종목 상세 (차트·뉴스 하위 화면 포함) | `app.html` iframe |
| `/buy/{코드}` · `/sell/{코드}` | 3단계 주문·이유 기록 | `app.html` iframe |
| `/tradingview-chart` | `lightweight-charts` 차트. `app.html` 내부 iframe에서 사용 | React |

- 로그인 화면은 라우트가 아니라 모든 주소의 분기다. 비로그인 상태로 어느 주소에 들어와도 `LoginGate`가 뜨고, 로그인하면 그 주소의 화면으로 간다.
- `/stocks`·`/trade/[symbol]`·`/archive`용 별도 페이지 파일은 **없다**. `web/app/` 아래 `archive/`·`stocks/`·`trade/[symbol]/`은 최초 스캐폴드의 `.gitkeep` 자리표시자뿐이라 라우트가 아니다(`/archive`는 캐치올이 받는다). `/feed`는 아예 없다.
- 나가는 방향(화면 → 주소)은 `app.html`이 보내는 `kiwoom:screen` 메시지가 정하고, 들어오는 방향(주소 → 화면)은 `actionFromRoute`가 만든 `open_screen` 액션이 정한다.

첫 진입 튜토리얼은 현재 사용자 흐름에 없다. 어디서도 로드하지 않던 `web/public/ui/tutorial.js`는 삭제했다.

### 4.1 가입 마법사는 목업이다 [사실]

부모 4단계·자녀 3단계 가입 마법사(`web/app/SignupWizard.tsx`)는 **화면 시연용 목업으로 확정됐다.** 서버 저장을 붙이지 않는 것이 결정이며, 미구현 결함이 아니다.

- 앱 안에서 새 가족·새 계정을 만드는 흐름은 없다. 계정은 Supabase에서 직접 만든다.
- 마법사 완료는 골든 패스에 넣지 않는다.
- `POST /api/auth/signup` 같은 경로를 새로 만들지 않는다.

### 4.2 계정 전환은 로그인·로그아웃이다 [사실]

다른 가족 구성원 화면을 보는 방법은 **로그아웃 → 해당 계정으로 재로그인** 하나로 확정됐다. 앱 안 계정 스위처 UI는 만들지 않는다.

- 로그아웃은 `app.html` 메뉴의 `DELETE /api/auth/login`이다.
- `POST /api/auth/switch`는 구현돼 있으나 **화면이 호출하지 않는다.** 이 방식이 확정된 이상 살릴 계획이 없는 미사용 경로이므로, 정리 대상으로 둔다.
- F11 수익률 탭의 구성원 필터는 열람 대상만 거르며 세션(`kw_uid`)을 바꾸지 않는다. 이는 전환이 아니다.

## 5. 주문·기록 흐름

### 5.1 매수

1. 시장가 또는 지정가와 금액/수량을 고른다.
2. 6개 매수 이유 중 하나를 고르고 메모를 선택 입력한다.
3. 4개 보유 계획 중 하나를 고른 뒤 주문한다.
4. 정규장 시장가는 즉시 체결한다. 장외 시장가는 현금을 예약한 `scheduled` 기록을 만들고 다음 거래일의 확인된 일봉 시가로 체결한다. 지정가는 현금을 예약한 pending 기록만 만든다.

현재 매수 이유는 뉴스·차트·익숙함·랭킹·주변 의견·직감 6개다. 계획은 단기·시즌·목표가·미정 4개다. **확신도 입력은 없다.** 목표가는 사용자가 스스로 적는 보유 계획이며 AI 추천 목표가가 아니다.

### 5.2 매도

1. 시장가 또는 지정가와 금액/수량을 고른다.
2. 6개 매도 이유 중 하나를 고른다.
3. 기존 계획 준수 여부를 기록하고, 계획과 다르면 5개 변경 이유 중 하나를 고른다.
4. 정규장 시장가는 즉시 반영한다. 장외 시장가는 수량을 예약한 `scheduled` 기록을 만들고 다음 거래일의 확인된 일봉 시가로 체결한다. 지정가는 pending 기록을 만든다.

장외 시장가 예약은 주문 접수와 실제 체결을 분리한다. 휴일·거래정지·시가 데이터 미확인 때는 예약을 유지하고, 같은 주문을 중복 체결하지 않는다. 금액 매수는 예약 금액 전부를 시가 기준 소수 수량으로 바꾸며, 수량 매수는 시가 상승으로 예약 금액을 넘으면 거절하고 현금을 돌려준다. 매도 예약과 지정가 매도는 보유 수량에서 사용 가능 수량만 잠그며 취소 시 자산 총액이 변하지 않는다. 지정가 주문은 자동 체결되지 않는다.

## 6. 저장과 서버 동기화

### 6.1 브라우저 즉시 상태

저장은 **오래 남는 것과 화면 임시값 두 덩어리**로 나뉜다. 화면을 실제 라우트로 옮기면 이동할 때마다 문서가 갈아끼워져 메모리 상태가 사라지므로, 작성 중이던 주문이 랭킹 탭 한 번에 날아가지 않게 임시값을 따로 넘긴다(PR #203).

| 저장소 | 키 | 값 | 수명 |
|---|---|---|---|
| `localStorage` | `kw_proto_v1` | 계정별 현금·보유, 매수·매도 기록, 행동 이벤트, 시퀀스, 관심 종목 | 새로고침해도 유지 |
| `sessionStorage` | `kw_proto_ui_v1` | 현재 화면·선택 계정·종목 코드·매수/매도 초안·주문 단계·아카이브 탭 | **앱 안에서 화면을 옮길 때만** 되살린다 |
| `sessionStorage` | `kw_proto_nav_v1` | `leaveToRoute()`가 남기는 "앱 안에서 넘어왔다" 표시 | 되살린 직후 지운다 |

배지 적립은 폐기돼 더 이상 저장하지 않는다. 표시가 없는 진입(F5·새 탭·주소 직접 입력)에서는 화면 임시값을 버려 **"F5 하면 처음부터"** 동작을 지킨다. 스쿨락 개발 설정은 어느 쪽에도 저장하지 않는다.

읽는 쪽은 `shared/store/prototype-account.js`의 `restorePrototypeState()` 하나이고 **첫 렌더 전에** 부른다(PR #217). `componentDidMount`에서 되살리던 예전 방식은 화면을 옮길 때마다 시드 지갑이 한 프레임 먼저 보였다 바뀌었다.

### 6.2 서버 연결

| 흐름 | 현재 동작 |
|---|---|
| `/api/auth/login` | 로그인(POST)은 `LoginGate`가, 로그아웃(DELETE)은 `app.html` 메뉴가 호출한다 |
| `/api/auth/switch` | 구현돼 있으나 화면이 호출하지 않는다 |
| `/api/account` | DB 사용자를 찾고, **로그인한 역할의 현금·보유를 서버 값으로 덮어쓴다**(`applyServerHoldings`). 반대쪽 역할은 로컬 데모 값으로 남는다 |
| `/api/trade` | DB 사용자와 현재 역할이 맞는 시장가 체결만 best-effort 전송. 실패해도 로컬 체결을 되돌리지 않음 |
| `/api/orders` | 미체결 주문(지정가 대기·장외 예약) 조회(GET)와 만기 예약 정산(POST). **구현돼 있으나 화면이 호출하지 않는다** — 예약은 아직 로컬 `acc.pending`이 돈다 |
| `/api/tab-view` | 종목 상세 탭 열람을 카테고리·종목별 카운트로 적재 |
| `/api/profile` | 구현돼 있으나 **화면이 호출하지 않는다.** 아카이브는 아래 두 경로만 부른다 |
| `/api/profile/behavior` | 로그인 세션의 DB 행동 집계로 캐릭터 카드만 다시 정함 |
| `/api/profile/season-cards` | 로그인 세션의 DB 매수를 주 단위로 묶은 지난 주차 카드 |
| `/api/family` · `/api/comments` · `/api/likes` | 가족 구성원·거래와 코멘트·좋아요. **원본이 DB다** |
| `/api/news`, `/api/news/[newsId]` | 검수를 통과한 어린이 뉴스 목록·상세 |

즉, 주문·보유의 체감 원본은 여전히 브라우저 상태이지만 **로그인·가족·반응·성향 조회는 DB가 원본**이다.

### 6.3 원본이 두 갈래인 이유와 현재 위치 [사실]

`app.html`은 원래 서버 없이 `localStorage` 하나로 도는 프로토타입이었다. 이후 기능별로 Supabase를 붙였지만 **기존 로컬 상태를 걷어내지 않고 위에 얹었기 때문에** 원본이 둘로 갈렸다. 의도한 설계가 아니라 **이행이 절반 끝난 상태**다.

| 데이터 | 현재 원본 | 배경 |
|---|---|---|
| 현금·보유·매수매도 기록·행동 이벤트 | `localStorage` `kw_proto_v1` | 프로토타입 때부터 있던 경로 |
| 로그인·가족·코멘트·좋아요·행동 집계·뉴스 | Supabase | 나중에 DB부터 만든 경로 |

쓰기 경로는 **로컬 먼저, 서버는 조건부 best-effort**다.

- `persist()`가 무조건 먼저 `localStorage`에 쓰고, 화면은 그 값을 읽는다.
- `saveTrade()`는 `dbSyncable()`(= DB 사용자 로드됨 **그리고** 현재 화면 계정 == 로그인 역할)일 때만 `POST /api/trade`를 보내고, 실패는 삼킨다.
- 따라서 조건이 어긋난 체결은 로컬에만 남고 DB에는 영영 들어가지 않는다.

읽기 경로는 한 방향으로 좁혀졌다. `applyServerHoldings`가 **로그인한 역할의 현금·보유는 DB 값으로 덮어쓴다.** 그래서 DB 저장이 실패한 체결은 화면상 체결로 보이다가 **다시 로드하면 사라질 수 있다**(§10-2). 근본 해결은 로컬 상태를 걷어내고 DB를 유일 원본으로 만드는 것이다.

### 6.4 서버 주문 생애주기 — 스키마만 먼저 갔다 [사실]

마이그레이션 `20260815033308_order_lifecycle_db_ownership`이 `transactions`에 주문 생애주기를 넣었다. **스키마와 API는 있고 화면 연결만 없다.**

- 상태 다섯 개는 화면이 쓰던 값을 그대로 옮겼다: `filled` · `pending`(지정가 대기) · `scheduled`(다음 거래일 시가) · `cancelled` · `rejected`.
- 예약 자원은 총량에서 잠근 양을 빼는 방식이다 — 현금은 `account.reserved_balance`, 수량은 `holdings.reserved_quantity`. 잔고를 직접 깎지 않으므로 예약·취소가 총자산을 바꾸지 않는다.
- **`transactions`에 미체결 행이 섞이므로 거래를 읽는 모든 경로는 `order_status='filled'`을 걸러야 한다.** 공용 헬퍼는 `app/api/supabase.ts`의 `selectFilledTrades`이며, 주문 자체를 다루는 `api/orders`만 `selectRows`를 직접 쓴다.
- 화면의 예약은 아직 로컬 `acc.pending`과 `features/f2-trade/lib/scheduled-orders.js`가 돌린다. 즉 브라우저를 지우면 예약은 여전히 사라진다(§10-7).

## 7. F9 계산과 표시

아카이브 탭은 **성향·수익률 두 개**이고, 성향 탭에서 카드 모아보기·카드 상세·가족 성향 비교 오버레이 셋이 열린다.

계산 엔진은 **두 벌이며 역할이 다르다**. 로그인 상태의 정본은 `shared/engine/behavior-profile.ts`(전 축 **0~10**, 5가 중립)이고 화면이 이를 그대로 읽는다. `shared/engine/archive-profile.js`(0~100)는 비로그인이거나 서버 응답이 오기 전의 폴백과 행동 신호 캐릭터 판정에 남아 있다.

| 경로 | 무엇을 주나 |
|---|---|
| `shared/engine/behavior-profile.ts` | 로그인 정본 — 다섯 축 0~10, 캐릭터, 정확 레벨, 주간 결산 카드 |
| `shared/engine/archive-profile.js` | 비로그인·응답 전 폴백 — `kw_proto_v1`로 계산하는 0~100 값 |
| `GET /api/profile/behavior` | 로그인 세션의 행동 집계로 **캐릭터 카드만** 다시 정한다 |
| `GET /api/profile/season-cards` | 로그인 세션의 Supabase 기록을 KST 주 단위로 묶은 지난 주차 카드 |
| `POST /api/profile` | 누적 스냅샷·주간 카드·선택적 Luna 서술을 계산하지만 **화면이 호출하지 않는다** |
| `GET /api/family` | 실제 가족 구성원, 누적 성향, **구성원별 수익률**(가족 비교 오버레이 + 수익률 탭 달리기 트랙) |
| `shared/engine/portfolio-return.ts` | 평가액·원금·수익률 산식. 금액과 비율을 나눠 돌려주므로 서버가 타인에게는 `returnRate`만 넘길 수 있다 |

주차 카드를 내는 곳은 둘이지만 산식은 `computeBehaviorProfile` 한 벌이다.

`app.html`이 실제로 부르는 프로필 경로는 `GET /api/profile/behavior`와 `GET /api/profile/season-cards` 둘뿐이다. `POST /api/profile`은 어느 화면도 호출하지 않으므로 **F9 화면에는 Luna 서술이 전혀 노출되지 않는다** — 아카이브에 보이는 값은 모두 `shared/engine` 계산 결과다.

### 7.1 Luna 서술이란 [사실]

캐릭터 카드에 붙일 **`gpt-5.6-luna`가 쓴 2~3문장 한국어 설명**이다. 구현은 `web/features/f9-archive/lib/narration.ts`에 있고 `POST /api/profile`만 이를 호출한다.

- 모델이 말해도 되는 숫자는 `allowedNumbers()`가 엔진 산출값·산식 상수로 제한하고, 출력은 `shared/llm/filter`의 `gateChatOutput`을 통과해야 한다.
- LLM 실패·미사용 시에는 `fallbackNarration()`의 룰 기반 고정 문구가 나간다(숫자 없는 해요체, 훈계·추천 없음).
- 반환 `source`가 `luna`인지 `fallback`인지로 어느 쪽이 나갔는지 구분한다.

**현재는 배선만 없는 상태다.** 살리려면 화면이 `POST /api/profile`을 부르게 하면 되고, 쓰지 않기로 하면 `narration.ts`와 `POST /api/profile`을 함께 지운다(§10-5).

- 유효 정보 확인: 매수 전 본 서로 다른 종목 상세 탭 수
- 집중/분산: 유효 섹터 수와 투자 비중
- 정확: 정본은 체결 후 **2거래일**, 폴백은 **5거래일** 종가 비교
- 매수 표본이 3건 미만이면 분석 데이터가 부족한 상태로 본다.

화면은 `LV` 레벨 표기를 쓴다. 폐기된 5축(`AXES`)과 별(★) 표기는 현재 실행 경로에서 사라졌고 레거시 목업 파일에만 남아 있다. 가족 비교의 동의 문구는 실제 동의 데이터가 아닌 고정 문구다. 상세 계산은 F9 SPEC을 따른다.

## 8. F11 피드와 차트 마커

- 피드: `GET /api/family`가 세션 사용자와 같은 `family_tag`의 구성원·Supabase 체결을 최신순으로 준다. 로컬 시드 피드와 `kiwoom-family-feed` 저장소는 제거됐다
- 차트 마커: `/api/trades`가 돌려주는 Supabase 거래만 사용
- 코멘트·좋아요: `/api/comments`·`/api/likes`를 통해 DB에 저장한다. 좋아요는 가족 전체 개수와 본인 선택 상태를 유지하고, 코멘트는 본인 것만 삭제할 수 있다
- 타인 카드의 수량·체결가는 서버 응답 단계에서 `null`로 마스킹한다
- 부모→자녀 코멘트의 추천·타이밍·훈계·채점 표현은 서버가 저장 전에 차단한다
- 피드는 `app.html` 아카이브 수익률 탭 **한 곳에만** 있다. React 오버레이 `FeedScreen`은 어디서도 import되지 않아 삭제했다
- 표시는 `tradedAt` 내림차순 **최근 12건**까지이고 종목 이동 버튼은 없다

피드와 차트가 이제 같은 거래 원본(Supabase `transactions`)을 본다. 상세 계약은 F11 SPEC을 따른다.

## 9. 현재 도달 가능한 골든 패스

1. `/`에서 아이디·비밀번호로 로그인하면 계정에 맞는 홈이 열린다.
2. 홈에서 가족 순위와 자녀 자산을 본다.
3. 모의투자 탭에서 종목을 탐색하고 상세 탭을 10초 이상 확인한다.
4. 상세에서 키웅이를 열어 허용 질문을 묻는다.
5. 정규장에는 매수 화면에서 시장가·금액, 이유, 보유 계획을 선택해 즉시 체결한다. 장외에는 같은 주문이 다음 거래일 시가 예약으로 접수되는지 확인한다.
6. 포트폴리오와 아카이브에서 새 로컬 거래가 반영됐는지 본다.
7. 가족 기록에서 가족 구성원의 DB 거래를 보고 좋아요와 코멘트를 남긴다. 다시 열어도 유지된다.
8. 종목 이동 버튼으로 해당 종목 상세가 열리는지 확인한다.

가입 완료, 튜토리얼, 지정가 자동 체결, 실제 시간외 거래는 이 골든 패스에 넣지 않는다. 계정 전환은 로그아웃 후 재로그인(§4.2)이므로 1번 단계로 되돌아가는 것과 같다.

## 10. 문서화된 현재 제약

여기 있는 항목은 **고쳐야 할 것**이다. 목업으로 확정된 가입 마법사(§4.1)와 로그인·로그아웃으로 확정된 계정 전환(§4.2)은 설계 결정이므로 제약이 아니다.

1. 정적 `app.html`이 주요 UI와 상태를 함께 소유해 기능 폴더 경계와 다르다.
2. 로컬 체결 성공과 서버 저장 성공이 원자적으로 묶여 있지 않다. 주문·보유의 체감 원본은 여전히 브라우저다(§6.3).
3. F11 카드의 금액은 총 거래금액이 아니라 **주당 체결가**인데 라벨이 그 구분을 하지 않는다. 매수·매도 양쪽 모두 해당하고, 남의 카드는 서버 마스킹으로 `비공개`라서 본인 카드에서만 보인다.
4. `profiles.login_password`가 아직 평문이다. 세 계정을 심는 마이그레이션은 생겼지만(`20260815033156_seed_family_profiles.sql`) 비밀번호는 커밋할 수 없어 `CHANGE_ME` 자리표시자이고, 실제 값은 배포 후 콘솔에서 직접 넣어야 한다.
5. `POST /api/profile`(F9 Luna 서술)·`POST /api/auth/switch`·`/api/orders`를 어느 화면도 호출하지 않는다. 살릴지 지울지 결정이 필요하다(§6.2·§7).
6. 수익률 탭에서 뺀 `보유 종목 · 섹터별` 레일 때문에 섹터 상세 모달(`secModal*`)과 `retSectors` 계산이 화면에서 도달 불가로 남아 있다.
7. 주문 생애주기가 DB에 생겼는데 화면은 아직 로컬 `acc.pending`으로 예약을 돌린다(§6.4). 브라우저를 지우면 예약이 사라지고, 서버는 예약이 잡아 둔 현금·수량을 모른다.
8. 화면 해체가 중간이다. `/ranking`만 React로 옮겨졌고 나머지는 `app.html`이 그린다. 그래서 폰 프레임 기하(`lib/phone-frame.ts`)와 오버레이 자르기(`phoneScreenClipPath`)를 두 경로가 같은 값으로 유지해야 한다.
9. `web/app/` 아래 `archive/`·`stocks/`·`trade/[symbol]/`이 최초 스캐폴드의 `.gitkeep`만 담은 채 남아 있다. 라우트로 동작하지는 않지만 라우트가 있는 것처럼 보인다.
