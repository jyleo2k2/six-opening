## 2. 실제 런타임 구조

```text
Next.js [[...screen]]
└─ web/app/[[...screen]]/page.tsx   (routeFromPath로 주소 해석 + kw_uid 세션 쿠키 확인)
   ├─ 모르는 주소 → notFound()
   ├─ 비로그인   → LoginGate  (스플래시 + 로그인 폼, SignupWizard 화면)
   └─ 로그인     → ConnectedPrototype  (주소와 무관하게 항상 이것 하나)
      ├─ 화면 (PhoneFrame + BottomNav)
      │  ├─ 홈 HomeScreen · 탐색 ExploreScreen · 계좌 PortfolioScreen · 랭킹 RankingScreen
      │  ├─ 아카이브 ArchiveScreen (성향·수익률 2탭 + 카드 모아보기·가족 비교)
      │  ├─ 종목 DetailScreen → ChartScreen(iframe /tradingview-chart) · NewsScreen
      │  └─ 주문 OrderScreen (매수·매도 3단계)
      ├─ F10 ChatbotOverlay
      └─ 폰 프레임 이미지 한 겹 (z-index 20)
```

**화면 해체가 끝났다** [사실 — PR #254]. 사용자 화면은 **홈·탐색·종목·계좌·랭킹·아카이브·주문 7개**이고(PR #224·#229·#232·#233·#238·#254), 목록의 원본은 `screen-route.ts`의 `ScreenRoute`다. `ScreenRoute`가 만들 수 있는 화면이 이 일곱뿐이므로 **어떤 주소로 들어와도 사용자가 보는 것은 React 화면이다.**

F11 가족 기록에는 전용 React 오버레이가 없다. 피드는 `ArchiveScreen`의 **수익률(`return`) 탭** 안에 있다.

**iframe과 조립기는 철거했다** [사실 — PR #296]. `web/public/ui/app.html`·`web/ui-src/`·`web/scripts/ui-build.mjs`가 전부 사라졌다. 되살리지 않는다.

걷어낼 수 있었던 것은 **남겨 둔 이유가 실측이었기 때문**이다. 화면 배율을 `app.html`이 자기 뷰포트로 정했으므로 `ConnectedPrototype`이 iframe 안 `#kw-screen`을 `ResizeObserver`로 재서 챗봇 시트와 폰 프레임 위치를 맞췄다. 그런데 재 보니 그 배율식과 `getPrototypeScreenRect(창너비, 창높이)`가 **항등이었다** — 여백이 대칭이라(24+402+24=450, 23+874+23=920) 잴 것이 없었다. 14개 뷰포트에서 확인한 뒤 순수 계산으로 바꿨고, 그러자 문서를 살려 둘 이유가 사라졌다.

그래서 지금 화면 사각형은 `getPrototypeScreenRect` 하나가 정하고, 기하 상수의 원본은 `f10-chatbot/lib/bottom-sheet`의 `PROTOTYPE_PHONE`이다. 챗봇 시트·`PhoneFrame`·오버레이 자르기(`phoneScreenClipPath`)가 모두 같은 값을 쓴다 — **배율을 다시 계산하지 않는다.**

옮긴 화면의 공용 조각은 `PhoneFrame`(폰 프레임)과 `BottomNav`(하단 탭 4개: 홈 / 모의투자 / 아카이브 / 랭킹)다. `BottomNav`는 이동을 직접 하지 않고 `onLeave`로 올린다 — 화면 이동은 `ConnectedPrototype`이 소유하며 문서를 갈아끼우지 않고 주소만 바꾼다.

폰 프레임 이미지는 **화면·챗봇보다 위에 한 겹 더** 깐다. 챗봇 시트처럼 올라오는 것들은 `PhoneFrame` 밖에 있어 프레임 이미지보다 위에 그려지고, 화면 사각형으로 자르더라도 화면 라운드(40px)보다 프레임 개구부가 깊어 그 틈으로 베젤 위에 비친다. 맨 위 한 겹이 있으면 무엇이 올라오든 베젤이 이긴다.

### 2.1 사용자 라우트

주소는 `features/f0-home/screen-route.ts`가 소유한다. `routeFromPath`가 아는 주소만 앱이고, **나머지는 404다**(오타가 조용히 홈으로 넘어가지 않는다).

| 경로 | 현재 역할 | 렌더링 |
|---|---|---|
| `/` | 홈 | **React `HomeScreen`** |
| `/explore` · `/explore/{섹터}` | 51종 종목 탐색. 섹터 칸은 `rank`(기본)·`watch`·유니버스 섹터 id | **React `ExploreScreen`** |
| `/ranking` | 가족 리그 순위 | **React `RankingScreen`** |
| `/portfolio` | 보유 자산 | **React `PortfolioScreen`** |
| `/archive` · `/archive/{자리}` | 성향·수익률 2탭. 자리는 `report`(기본, 주소에 안 적음)·`return`·`cards`·`family`·`last`(지난 시즌 리포트) | **React `ArchiveScreen`** |
| `/stock/{6자리코드}` | 종목 상세 (차트·뉴스 하위 화면 포함) | **React `DetailScreen`** |
| `/buy/{코드}` · `/sell/{코드}` | 3단계 주문·이유 기록 | **React `OrderScreen`** |
| `/tradingview-chart` | `lightweight-charts` 차트. `ChartScreen`이 iframe으로 연다 | React |

- 로그인 화면은 라우트가 아니라 모든 주소의 분기다. 비로그인 상태로 어느 주소에 들어와도 `LoginGate`가 뜨고, 로그인하면 그 주소의 화면으로 간다.
- `/stocks`·`/trade/[symbol]`·`/feed` 라우트는 **없다**. `web/app/` 아래에 있던 `archive/`·`stocks/`·`trade/[symbol]/` 빈 스캐폴드 폴더는 PR #223에서 삭제했다. `/archive`는 캐치올이 받는다.
- 화면끼리의 이동은 `onLeave(경로)` → `ConnectedPrototype.openRoute` 하나로 모이고 `history.replaceState`로 주소만 바꾼다(히스토리를 쌓지 않는다 — 앱 안 뒤로가기와 어긋나므로).
- **`postMessage` 계약은 하나만 남았다.** `ChartScreen`이 `/tradingview-chart` iframe에 보내는 `kiwoom:chart-options`와 그쪽이 돌려주는 `kiwoom:chart-ready` 한 갈래다. 옛 화면 이동 계약(`kiwoom:screen`·`kiwoom:open-route`·`kiwoom:open-stock`)은 수신부와 함께 사라졌다 — 새 메시지 계약을 늘리지 않는다.

### 4.1 가입 마법사는 목업이다 [사실]

부모 4단계·자녀 3단계 가입 마법사(`web/app/SignupWizard.tsx`)는 **화면 시연용 목업으로 확정됐다.** 서버 저장을 붙이지 않는 것이 결정이며, 미구현 결함이 아니다.

- 앱 안에서 새 가족·새 계정을 만드는 흐름은 없다. 계정은 Supabase에서 직접 만든다.
- 마법사 완료는 골든 패스에 넣지 않는다.
- `POST /api/auth/signup` 같은 경로를 새로 만들지 않는다.

### 4.2 계정 전환은 로그인·로그아웃이다 [사실]

다른 가족 구성원 화면을 보는 방법은 **로그아웃 → 해당 계정으로 재로그인** 하나로 확정됐다. 앱 안 계정 스위처 UI는 만들지 않는다.

- 로그아웃은 홈 화면(React `HomeScreen`) 메뉴의 `DELETE /api/auth/login`이다.
- `POST /api/auth/switch`는 **PR #221에서 삭제했다.** 어느 화면도 부르지 않았고 이 방식이 확정된 이상 살릴 계획이 없었다. `web/app/api/auth/`에는 `login`만 남는다.
- F11 수익률 탭의 구성원 필터는 열람 대상만 거르며 세션(`kw_uid`)을 바꾸지 않는다. 이는 전환이 아니다.

### 4.3 세션은 서버 부팅 표식이 정한다 [사실 — PR #240·#245]

앱을 다시 열면 로그인 화면부터 시작한다. PR #240이 `kw_uid`에서 30일 `Max-Age`를 빼 브라우저 세션 쿠키로 바꿨지만 그것만으로는 부족했다 — `Set-Cookie`는 새로 발급하는 쿠키에만 적용돼 **이미 나간 30일짜리 쿠키가 그대로 남았고**, 크롬·엣지의 "이전에 열었던 페이지 계속 보기"는 세션 쿠키까지 복원했다.

그래서 언제 로그아웃할지를 브라우저가 아니라 **서버가 정한다.**

- 프로세스가 뜰 때 부팅 표식을 만들어 쿠키 값에 `사용자id.표식`으로 넣고, 읽을 때 지금 표식과 대조한다. 다르거나 없으면 비로그인이다(표식 없는 옛 쿠키도 함께 걸러진다).
- 표식은 `globalThis`에 둔다. Next가 서버 컴포넌트와 라우트 핸들러를 다른 모듈 그래프로 불러도 기준이 갈리지 않고, 개발 중 모듈이 다시 평가돼도 작업하다 말고 로그아웃되지 않는다.
- 쿠키 해석은 `app/api/supabase.ts`의 `sessionUserIdFromCookie` 하나가 한다. 화면(`page.tsx`)과 API가 같은 함수를 쓴다.
- 서버를 재시작하면 모든 세션이 끊긴다. 개발 중 `npm run dev`가 다시 뜰 때마다 다시 로그인해야 한다.

### 4.4 스쿨락은 꺼 두기로 했다 [사실 — 2026-08-16 확정]

자녀 매매 잠금(평일 09:00~15:30)은 **끈 상태가 현재 결정이다.** `lib/use-wallet.ts`의 `SCHOOL_LOCK_ENABLED = false` 한 곳이 정한다.

끈 이유는 **그 창이 정규장 창(`isRegularMarketOpen`)과 정확히 같기 때문**이다.

| 시간대 | 스쿨락이 켜져 있었을 때 자녀가 할 수 있는 것 |
|---|---|
| 평일 09:00~15:30 | 주문 단계(`locked && step === 2`)에서 막혀 **질문식 매매를 끝까지 진행할 수 없다** |
| 그 밖 | 주문은 되지만 정규장이 아니라 다음 거래일 시가 예약이 된다 |

즉 **자녀 계정으로 즉시 체결을 볼 수 있는 시간대가 존재하지 않았다.** 두 창이 같다는 사실은 `use-wallet.test.ts`가 지킨다 — 어느 한쪽 창이 바뀌면 그 테스트가 깨지고, 그때 다시 켤지 검토한다.

보여 줄 기능도 아니다. 중간발표 대본 v2 12슬라이드에 등장하지 않고, 통합문서 v2에는 "스쿨락 15:00 / 문구 16:00 불일치 해소" 체크리스트로 한 번 나오며, 골든 패스(§9)에도 단계가 없다. 와이어프레임브리프는 스쿨락 카드가 부모 전용이고 일반 사용자 흐름에서 열 수 없다고 적는다.

- 화면의 `locked` 분기는 지우지 않았다. 종목 상세 하단(`lib/stock-chrome.tsx`)과 계좌(`PortfolioScreen`)의 `지금은 학교에서 공부할 시간!` 안내는 코드에 남아 있고 지금은 그려지지 않는다.
- 되살리려면 `SCHOOL_LOCK_ENABLED`만 `true`로 되돌린다.
- **챗봇은 아직 이 기능을 안내한다** — §10-4.

## 5. 주문·기록 흐름

### 5.1 매수

1. 시장가 또는 지정가와 금액/수량을 고른다.
2. 6개 매수 이유 중 하나를 고르고 메모를 선택 입력한다.
3. 4개 보유 계획 중 하나를 고른 뒤 주문한다.
4. 정규장 시장가는 즉시 체결한다. 장외 시장가는 현금을 예약한 `scheduled` 주문을, 지정가는 현금을 예약한 `pending` 주문을 **서버에 접수한다**(§6.4).

매수 이유 버튼 순서는 진입할 때마다 섞는다(F3 SPEC). 매수 완료에는 풍선·색종이·곰 등장 연출이 붙고, 매도 완료에는 원본대로 연출이 없다 [사실 — PR #256에서 `phone-frame.css`에 keyframes를 복원했다. 이관 과정에서 마크업만 남고 정의가 사라져 조용히 죽어 있었다].

현재 매수 이유는 뉴스·차트·익숙함·랭킹·주변 의견·직감 6개다. 계획은 단기·시즌·목표가·미정 4개다. **확신도 입력은 없다.** 목표가는 사용자가 스스로 적는 보유 계획이며 AI 추천 목표가가 아니다.

### 5.2 매도

1. 시장가 또는 지정가와 금액/수량을 고른다.
2. 6개 매도 이유 중 하나를 고른다.
3. 기존 계획 준수 여부를 기록하고, 계획과 다르면 5개 변경 이유 중 하나를 고른다.
4. 정규장 시장가는 즉시 반영한다. 장외 시장가는 수량을 예약한 `scheduled` 주문을, 지정가는 `pending` 주문을 **서버에 접수한다**(§6.4). 매도 이유 버튼은 앞 5개만 섞는다.

장외 시장가 예약은 주문 접수와 실제 체결을 분리한다. 휴일·거래정지·시가 데이터 미확인 때는 예약을 유지하고, 같은 주문을 중복 체결하지 않는다. 금액 매수는 예약 금액 전부를 시가 기준 소수 수량으로 바꾸며, 수량 매수는 시가 상승으로 예약 금액을 넘으면 거절하고 현금을 돌려준다. 매도 예약과 지정가 매도는 보유 수량에서 사용 가능 수량만 잠그며 취소 시 자산 총액이 변하지 않는다. 지정가 주문은 자동 체결되지 않는다.

## 6. 저장과 서버 동기화

### 6.1 브라우저 저장소는 이제 쓰지 않는다 [사실 — PR #324]

**앱 데이터가 브라우저에 남지 않는다.** 마지막 칸이던 `localStorage`의 `kw_proto_v1`은 철거됐다.

| 예전에 저장하던 것 | 지금 원본 |
|---|---|
| 계정별 현금·보유 | `GET /api/account` |
| 미체결 주문 | `GET /api/orders` |
| 매수·매도 기록(이유·계획·메모) | `GET /api/trades` |
| 관심 종목 | `GET /api/watchlist` |
| 행동 이벤트 | `POST /api/tab-view` |

`kw_proto_v1`은 이 앱이 **서버 없이 정적 HTML 한 장으로 돌던 시절의 세이브 파일**이었다. 계좌도 DB도 없으니 사용자가 한 일을 어딘가 적어야 새로고침을 견뎠기 때문이다. 브라우저가 주인이라 기기를 바꾸면 통째로 사라졌고, 가족끼리 서로의 기록을 볼 수 없었으며, Supabase를 붙인 뒤로는 같은 값에 답하는 원본이 둘이 됐다. 그래서 조각조각 서버로 옮겼고(#246·#250 예약 → #243 현금·보유 → watchlist → **#324 매매 기록**) 이제 남은 것이 없다.

**마지막 조각이 매매 기록이었던 이유는 회고 판정이다.** 매도 2단계의 `사던 날의 나` 카드가 "이 종목을 언제 왜 샀는지"를 읽어야 하는데, 그 값이 지갑에만 있으면 **이 브라우저에서 산 것만** 기록이 있다. DB 시드로 심어진 보유를 팔거나 기기를 바꾸면 판정이 통째로 `null`이 되고, 카드가 안 뜨는 데 그치지 않고 `plan_match`가 빈 채로 저장돼 **F9 계획 준수 표본에서 조용히 빠졌다.** 지금은 `GET /api/trades?symbol=`이 그 값을 주며, 응답 행의 `mine` 플래그로 내 체결만 고른다(수량 마스킹의 부산물인 `quantity !== null`에 기대면 마스킹 규칙이 바뀔 때 조용히 어긋난다).

`useWallet`의 지갑은 이제 **메모리 전용**이다. 마운트마다 서버로 세우고 화면을 떠나면 사라진다. `update()`는 체결 직후 완료 화면이 잔액을 바로 보여 주기 위한 갱신일 뿐이고 곧 `refresh()`가 서버 값으로 덮으므로, **거기 남은 값을 원본으로 믿으면 안 된다.**

새 값을 화면에 얹기 전에 **그것을 담을 서버 경로가 먼저 있어야 한다.** `screen-state-handoff.test.ts`가 이 계약을 지킨다 — `kw_proto_v1`·`kw_proto_ui_v1`·`kw_proto_nav_v1` 세 키가 코드에 다시 나타나면 실패한다.

**탭 유효 열람(10초) 버퍼만 React 메모리에 있다** [사실 — PR #256]. `lib/tab-views.ts`가 상세·차트·뉴스 열람을 모아 두었다가 **매수 체결 때** `/api/tab-view`로 보낸다. 로그인 역할이 맞지 않으면 보내지 않고 **버린다** — 남겨 두면 다음 사용자의 체결에 남의 열람이 딸려 간다.

배지 적립은 폐기돼 더 이상 저장하지 않는다. 스쿨락도 저장할 설정이 없다 — 꺼진 채 고정이다(§4.4).

### 6.2 서버 연결

| 흐름 | 현재 동작 |
|---|---|
| `/api/auth/login` | 로그인(POST)은 `LoginGate`가, 로그아웃(DELETE)은 `HomeScreen` 메뉴가 호출한다 |
| `/api/account` | DB 사용자를 찾고, **로그인한 역할의 현금·보유를 서버 값으로 세운다.** 사용자 화면은 `useWallet`→`applyServerAccount`로 읽는다(PR #243). 반대쪽 역할은 시드 데모 값으로 남는다 |
| `/api/trade` | POST는 DB 사용자와 현재 역할이 맞는 **시장가 즉시 체결**을 `apply_trade` RPC로 반영한다. **응답을 확인한 뒤에야 완료 화면을 띄운다**(§6.3). PATCH는 **매도 완료 화면의 한 줄 메모**를 이미 남긴 기록에 단다 — 체결이 끝난 뒤 적으므로 `apply_trade`로는 들어올 수 없고, `set_trade_memo`가 `user_id`를 대조해 남의 기록을 막는다 |
| `/api/trades` | **매매 기록의 원본.** 차트 마커와 매도 회고 판정이 같이 쓴다. 응답 행의 `mine`으로 내 체결을 가른다 |
| `/api/orders` | **미체결 주문의 원본.** GET은 목록 조회이자 **만기 예약 정산 트리거**(멱등한 `settle_order`를 먼저 돌린다), POST는 지정가·장외 예약 접수(`reserve_order`가 한 트랜잭션에서 자원 잠금), DELETE는 취소(`cancel_order`가 `user_id`까지 대조). `useWallet`이 GET, `OrderScreen`이 POST, `PortfolioScreen`이 DELETE를 부른다 |
| `/api/tab-view` | 종목 상세 탭 열람을 카테고리·종목별 카운트로 적재. 버퍼는 `lib/tab-views.ts`이고 매수 체결이 방아쇠다(§6.1) |
| `/api/watchlist` | **관심 종목의 원본.** GET은 목록, POST는 토글이며 서버가 돌려준 목록으로 캐시를 통째로 갈아 끼운다. `lib/use-watchlist.ts` 하나가 읽는다 |
| `/api/profile/season-cards` | 로그인 세션의 DB 기록으로 만든 **아카이브 값의 유일한 통로**(누적 카드 + 주차 카드) |
| `/api/family` · `/api/comments` · `/api/likes` | 가족 구성원·거래와 코멘트·좋아요. **원본이 DB다** |
| `/api/news`, `/api/news/[newsId]` | 검수를 통과한 어린이 뉴스 목록·상세 |

즉 **앱 데이터의 원본은 전부 DB다.** 브라우저에만 남는 앱 데이터는 없다.

### 6.3 원본이 갈렸던 이유와 지금 [사실 — PR #324로 해소]

이 앱은 원래 서버 없이 `localStorage` 하나로 도는 프로토타입이었다. 이후 기능별로 Supabase를 붙였지만 **기존 로컬 상태를 걷어내지 않고 위에 얹었기 때문에** 원본이 둘로 갈렸다. 의도한 설계가 아니라 이행이 절반 끝난 상태였고, **이제 이행이 끝났다.**

| 데이터 | 원본 | 옮긴 시점 |
|---|---|---|
| 로그인·가족·코멘트·좋아요·행동 집계·뉴스 | Supabase | 처음부터 DB로 만든 경로 |
| 미체결 주문(지정가·장외 예약) | Supabase | PR #246·#250 (§6.4) |
| 현금·보유 | Supabase | PR #243 |
| 관심 종목 | Supabase | `/api/watchlist` 신설 |
| **매수·매도 기록**(이유·계획·메모) | Supabase | **PR #324 — 마지막 조각** |

**쓰기 순서도 한 가지로 통일됐다 — 서버가 확정한 뒤에 화면을 바꾼다.** 예약 주문의 "접수가 곧 주문"(§6.4)과 즉시 체결이 이제 같은 모양이다.

```
postTrade(...) → 실패·미전송이면 거절 문구(`주문을 넣지 못했어…`)로 끝낸다
              → 성공해야 finishBuy/finishSell 이 메모리 지갑을 바꾸고 완료 화면을 띄운다
```

- `syncable`(= DB 사용자 로드됨 **그리고** 현재 화면 계정 == 로그인 역할)이 아니면 보내지 않고 **`null`을 돌려주므로 같은 거절 분기로 간다.** 조용히 화면에만 남는 경로가 없다.
- 체결 뒤 `refresh()`는 잔액을 서버 값으로 맞추는 후속 동기화이지 체결의 근거가 아니다.
- 완료 화면의 `남은 지갑`만 `refresh()`를 기다리지 않고 미리 그린다 — 곧 서버 응답이 덮는 표시용 값이다.

즉 **로컬 성공과 서버 저장이 어긋나는 자리가 남아 있지 않다.**

`seedAccounts()`는 **응답이 오기 전과 서버를 못 읽었을 때만** 보이는 자리로 좁혀졌다. `useWallet`은 응답을 기다렸다 **한 번에** 세운다 — 시드를 먼저 그리고 덮으면 데모 지갑이 한 프레임 보였다 바뀐다.

### 6.4 서버 주문 생애주기 — 화면까지 연결됐다 [사실 — PR #246·#250]

마이그레이션 `20260815033308_order_lifecycle_db_ownership`이 `transactions`에 주문 생애주기를 넣었고, PR #250이 화면을 그 위에 붙였다. **미체결 주문의 원본은 이제 서버 하나다.**

- 상태 다섯 개는 화면이 쓰던 값을 그대로 옮겼다: `filled` · `pending`(지정가 대기) · `scheduled`(다음 거래일 시가) · `cancelled` · `rejected`.
- 예약 자원은 총량에서 잠근 양을 빼는 방식이다 — 현금은 `account.reserved_balance`, 수량은 `holdings.reserved_quantity`. 잔고를 직접 깎지 않으므로 예약·취소가 총자산을 바꾸지 않는다.
- **`transactions`에 미체결 행이 섞이므로 거래를 읽는 모든 경로는 `order_status='filled'`을 걸러야 한다.** 공용 헬퍼는 `app/api/supabase.ts`의 `selectFilledTrades`이며, 주문 자체를 다루는 `api/orders`만 `selectRows`를 직접 쓴다.
- **접수가 곧 주문이다.** `OrderScreen`은 예약 목록을 만들지도, 현금을 빼지도 않는다 — `POST /api/orders`가 실패하면 완료 화면 대신 거절 문구를 보여 주고, 성공하면 `refresh()`가 계좌와 주문 목록을 서버에서 다시 읽는다.
- **조회가 정산을 겸한다.** `GET /api/orders`가 만기 지난 예약을 먼저 처리하므로 `useWallet`의 조회 자체가 체결 트리거다. 화면은 시가를 따로 확인하지 않고, `settle_order`가 멱등이라 동시에 두 번 들어와도 중복 체결되지 않는다.
- 서버 응답을 화면이 쓰던 `pending` 모양으로 바꾸는 곳은 `features/f2-trade/lib/scheduled-orders.js`와 `f0-home/lib/pending-orders.ts`다. **화면이 스스로 정산하지 않는다는 계약을 `scheduled-orders.test.ts`가 지킨다** — 실제로 PR #252가 남긴 주석 한 줄이 이 가드에 걸려 `main`의 `npm test`가 깨진 적이 있다(PR #256에서 해소).

즉시 체결도 같은 규칙을 따른다. 시장가 체결은 `POST /api/trade` 응답을 확인한 뒤에 완료 화면을 띄우고, 실패하면 거절 문구를 보여 준다(§6.3).

## 7. F9 계산과 표시

아카이브는 React `ArchiveScreen`이며 **자리 넷**이다 — 성향 탭, 수익률 탭, 그리고 탭을 덮는 카드 모아보기·가족 비교(시트가 아니라 자리다). 카드 모아보기는 좌우로 끌어 넘기는 레일 하나이고(PR #239·#241), 예전의 별도 카드 상세 자리는 그 레일에 합쳐졌다.

**계산 엔진은 한 벌이다** [개정 2026-08-16 — PR #294]. 정본은 `shared/engine/behavior-profile.ts`(전 축 **0~10**, 5가 중립)이고, 화면에 닿는 통로는 `GET /api/profile/season-cards` 하나다.

그전에는 같은 질문에 답하는 산식이 셋이었다 — 로컬 구버전(0~100)·`GET /api/profile/behavior`의 행동 신호 근사·`season-cards` 누적 카드. 셋이 서로 다른 시점에 도착하면서 캐릭터가 `승부사 LV2 → 저격수 LV2 → 승부사 LV3`으로 번갈아 떴다. 지금은 **엔진이 판정을 보류하면 축은 중립 5, 유형은 `관찰 중`이고 구버전 산식으로 되짚지 않는다.**

| 경로 | 무엇을 주나 |
|---|---|
| `shared/engine/behavior-profile.ts` | 정본 — 다섯 축 0~10, 캐릭터, 정확 레벨, 주간 결산 카드 |
| `GET /api/profile/season-cards` | 그 엔진의 유일한 통로. 누적 카드 + KST 주 단위 주차 카드 |
| `GET /api/family` | 실제 가족 구성원, 누적 성향, **구성원별 수익률**(가족 비교 오버레이 + 수익률 탭 달리기 트랙) |
| `shared/engine/portfolio-return.ts` | 평가액·원금·수익률 산식. 금액과 비율을 나눠 돌려주므로 서버가 타인에게는 `returnRate`만 넘길 수 있다 |

`GET /api/profile/behavior`는 삭제됐다. `shared/engine/archive-profile.js`(0~100)는 **화면 연결이 끊긴 채 자체 테스트로만 남아 있다** — 판정에 쓰지 않는다.

아카이브가 부르는 서버 경로는 `lib/use-archive-data.ts` 하나로 모여 있다 — `GET /api/profile/season-cards`·`GET /api/family`, 그리고 피드 반응의 `/api/comments`·`/api/likes`. 주차 카드 산식은 `computeBehaviorProfile` 한 벌이다.

### 7.1 F9는 LLM을 쓰지 않는다 [사실 — 2026-08-15 확정]

아카이브에 보이는 값은 **전부 `shared/engine` 계산 결과**다. 캐릭터 카드에 `gpt-5.6-luna`가 쓴 설명을 붙이는 "Luna 서술" 경로(`POST /api/profile` + `f9-archive/lib/narration.ts`)가 있었지만 **어느 화면도 부른 적이 없어 PR #221에서 삭제했다.** 함께 지운 것은 그 라우트만 쓰던 `behavior-profile.ts`의 `parsePrototypeProfileInput`·`profileEntriesFromTrades`다.

서술을 다시 붙이기로 하면 SPEC에 계약부터 적고 화면 연결까지 한 작업으로 처리한다. 예전 구현을 되살리지 않는다.

- 유효 정보 확인: 매수 전 본 서로 다른 종목 상세 탭 수
- 집중/분산: 유효 섹터 수와 투자 비중
- 정확: 체결 후 **2거래일** 종가 비교
- 매수 표본이 3건 미만이면 분석 데이터가 부족한 상태로 본다.

화면은 `LV` 레벨 표기를 쓴다. 폐기된 5축(`AXES`)과 별(★) 표기는 현재 실행 경로에서 사라졌고 레거시 목업 파일에만 남아 있다. 가족 비교의 동의 문구는 실제 동의 데이터가 아닌 고정 문구다. 상세 계산은 F9 SPEC을 따른다.

## 8. F11 피드와 차트 마커

- 피드: `GET /api/family`가 세션 사용자와 같은 `family_tag`의 구성원·Supabase 체결을 최신순으로 준다. 로컬 시드 피드와 `kiwoom-family-feed` 저장소는 제거됐다
- 차트 마커: `/api/trades`가 돌려주는 Supabase 거래만 사용
- 코멘트·좋아요: `/api/comments`·`/api/likes`를 통해 DB에 저장한다. 좋아요는 가족 전체 개수와 본인 선택 상태를 유지하고, 코멘트는 본인 것만 삭제할 수 있다
- 타인 카드의 수량·체결가는 서버 응답 단계에서 `null`로 마스킹한다
- 부모→자녀 코멘트의 추천·타이밍·훈계·채점 표현은 서버가 저장 전에 차단한다
- 피드는 `ArchiveScreen`의 수익률 탭 **한 곳에만** 있다(카드 조립은 `lib/archive-feed.ts`). 예전 React 오버레이 `FeedScreen`은 어디서도 import되지 않아 삭제했다
- 표시는 `tradedAt` 내림차순 **최근 12건**까지이고 종목 이동 버튼은 없다

피드와 차트가 이제 같은 거래 원본(Supabase `transactions`)을 본다. 상세 계약은 F11 SPEC을 따른다.

## 9. 현재 도달 가능한 골든 패스

1. `/`에서 아이디·비밀번호로 로그인하면 계정에 맞는 홈이 열린다.
2. 홈에서 가족 순위와 자녀 자산을 본다.
3. 모의투자 탭에서 종목을 탐색하고 상세 탭을 10초 이상 확인한다.
4. 상세에서 키웅이를 열어 허용 질문을 묻는다.
5. 정규장에는 매수 화면에서 시장가·금액, 이유, 보유 계획을 선택해 즉시 체결한다. 장외에는 같은 주문이 다음 거래일 시가 예약으로 **서버에 접수**되는지 확인한다.
6. 포트폴리오에서 새 거래와 기다리는 주문을 보고, 예약 하나를 취소해 잔액이 돌아오는지 본다. 아카이브에도 반영됐는지 확인한다.
7. 아카이브 수익률 탭에서 가족 구성원의 DB 거래를 보고 좋아요와 코멘트를 남긴다. 다시 열어도 유지된다.
8. 브라우저를 닫았다 다시 열면 로그인 화면부터 시작한다(§4.3).

가입 완료, 튜토리얼, 지정가 자동 체결, 실제 시간외 거래는 이 골든 패스에 넣지 않는다. 계정 전환은 로그아웃 후 재로그인(§4.2)이므로 1번 단계로 되돌아가는 것과 같다.

## 9.1 검증 장치 [사실 — PR #257]

`.github/workflows/web-ci.yml`이 PR마다 `web`에서 **`npm test` → F10 회귀 → `npm run build`**를 돌린다. 그전까지 CI는 세션 정책만 검사해 코드가 빌드되는지조차 보지 않았다.

- 비밀키 없이 통과해야 한다. 빌드가 환경변수를 요구하기 시작하면 CI가 먼저 잡는다.
- 조립 단계는 없다. `predev`·`prebuild`·`pretest` 훅은 iframe 철거와 함께 사라졌고(PR #296) `npm test` → F10 회귀 → `npm run build` 셋뿐이다.
- F10 회귀는 `records/f10-child-sim/run-regression.ts`이며 세트가 둘이다. `questions-v2.json`은 신규 기능 영역을, `questions-v3.json`(172건)은 **같은 취지·다른 표현** 축을 본다. 두 세트는 서로를 대체하지 않는다.
- **차단은 개별 케이스가 아니라 분포로 막는다.** 트리거를 넓히는 작업의 위험은 과차단이 아니라 과소차단이라, 600건에서 `refusal + safety >= 258`을 깨면 실행기가 exit 1 한다.

`web/design-system/`은 claude.ai/design에서 받아 온 **반입 원본**이다(PR #252). 빌드에 들어가지 않고 손으로 고치지 않으며, 화면이 쓰는 토큰·컴포넌트의 단일 원본은 여전히 `docs/디자인시스템.md`다.

## 10. 문서화된 현재 제약

여기 있는 항목은 **고쳐야 할 것**이다. 목업으로 확정된 가입 마법사(§4.1)와 로그인·로그아웃으로 확정된 계정 전환(§4.2)은 설계 결정이므로 제약이 아니다.

1. F11 카드의 금액(`archive-feed.ts`의 `avgText`)은 총 거래금액이 아니라 **주당 체결가**인데 라벨이 그 구분을 하지 않는다. 매수·매도 양쪽 모두 해당하고, 남의 카드는 서버 마스킹으로 `비공개`라서 본인 카드에서만 보인다.
2. `profiles.login_password`가 아직 평문이다. 세 계정을 심는 마이그레이션은 생겼지만(`20260815033156_seed_family_profiles.sql`) 비밀번호는 커밋할 수 없어 `CHANGE_ME` 자리표시자이고, 실제 값은 배포 후 콘솔에서 직접 넣어야 한다.
3. **챗봇이 없는 기능을 안내한다.** `shared/data/chatbot-knowledge.ts`의 `trade-lock`이 "주문 잠금은 **보호자가 정한 시간** 동안 자녀 계정의 주문만 잠시 막는 기능"이라 답하고 `actionTarget: "home"`으로 홈을 가리킨다(라우팅 테스트에도 `학교 시간엔 매매 쉬기 토글은 어떻게 써?` 케이스가 있다). 그런데 `HomeScreen`에 그런 토글이 없고, 스쿨락은 애초에 보호자가 정하는 값이 아니라 하드코딩된 시계였으며 지금은 아예 꺼져 있다(§4.4). 답변 문구를 실제 동작에 맞추거나 홈에 보호자 설정을 만들거나 둘 중 하나가 필요하다.
4. 아카이브의 `보유 종목 · 섹터별` 레일은 이관하면서 옮기지 않았다. 도달 불가였던 `secModal*`·`retSectors`는 함께 사라졌으므로 되살리려면 레일부터 다시 설계해야 한다.
5. **`shared/engine/archive-profile.js`(0~100)가 화면 연결 없이 남아 있다**(§7). 자체 테스트만 이 파일을 붙들고 있으므로 지울지 남길지 정해야 한다 — 남겨 두면 다음 세션이 폐기된 0~100 산식을 현행으로 오해한다.
