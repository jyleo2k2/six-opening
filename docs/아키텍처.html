2런타임 아키텍처

모든 사용자 요청은 캐치올 라우트 하나로 들어온다. 로그인 분기도 화면 선택도 여기서 끝난다.

브라우저 요청  (어떤 주소든)
  │
  └─ web/app/[[...screen]]/page.tsx          ← 서버 컴포넌트. 화면 진입점은 이것 하나
       │
       ├─ routeFromPath(pathname)            ← 아는 주소만 통과
       │     └─ 모르는 주소 → notFound()      (오타가 조용히 홈으로 넘어가지 않는다)
       │
       ├─ kw_uid 쿠키 → findProfileById()    ← 세션 확인, 서버에서만
       │     │
       │     ├─ 없음 → LoginGate             (스플래시 + 로그인 폼 + SignupWizard)
       │     │
       │     └─ 있음 → ConnectedPrototype    (227줄. 화면 전환을 혼자 소유)
       │                │
       │                ├─ PhoneFrame + BottomNav + 화면 7종
       │                │    홈 · 탐색 · 랭킹 · 아카이브 · 종목 · 차트 · 주문
       │                ├─ ChatbotOverlay      (F10 키웅이)
       │                ├─ TutorialOverlay     (챗봇 위, 프레임 아래)
       │                └─ 폰 프레임 이미지 한 겹  (z-index 20 — 무엇이 올라와도 베젤이 이긴다)
       │
       └─ /tradingview-chart                 ← lightweight-charts iframe. 유일한 예외 라우트
화면 이동은 한 갈래뿐 각 화면은 이동을 직접 하지 않는다. onLeave(경로)로 올리면 ConnectedPrototype.openRoute가 받아 history.replaceState로 주소만 바꾼다. 히스토리를 쌓지 않는 이유는 앱 안 뒤로가기와 어긋나기 때문이다.

iframe은 철거됐다

과거 화면은 public/ui/app.html iframe 안의 screen 상태가 소유했다. 지금은 전부 React다. iframe을 마지막까지 살려 둔 이유는 화면 사각형 실측이었는데, 재 보니 그 배율식과 순수 함수 getPrototypeScreenRect(창너비, 창높이)가 항등이었다 — 여백이 대칭이라 (24+402+24=450, 23+874+23=920) 잴 것이 없었다. 14개 뷰포트에서 확인한 뒤 걷어냈다.

남은 postMessage 계약은 하나뿐이다: ChartScreen → 차트 iframe의 kiwoom:chart-options와 회신 kiwoom:chart-ready. 옛 화면 이동 계약 (kiwoom:screen·kiwoom:open-route·kiwoom:open-stock)은 수신부와 함께 사라졌다. 새 메시지 계약을 늘리지 않는다.

3라우팅 계약

URL 계약 전체가 screen-route.ts의 함수 두 개다 — routeFromPath(주소 → 화면)와 pathFromRoute(화면 → 주소).

경로화면비고
/HomeScreen총자산·쓸 수 있는 돈·가진 회사
/explore · /explore/{섹터}ExploreScreen51종 탐색. 섹터 칸 = rank(기본)·watch·유니버스 섹터 id
/rankingRankingScreen가족 리그 순위
/archive · /archive/{자리}ArchiveScreen자리 = report(기본, 주소 생략)·return·cards·family·last

라우트가 아닌 것 /stocks · /trade/[symbol] · /feed · /portfolio 는 없다(404). 로그인 화면도 라우트가 아니라 모든 주소의 분기다 — 비로그인으로 어느 주소에 들어와도 LoginGate가 뜨고, 로그인하면 그 주소의 화면으로 간다.

챗봇이 화면을 여는 길

키웅이가 "성향 카드 보여줘"로 화면을 점프할 수 있다. 단, 모델이 만든 URL은 받지 않는다. 서버가 허용한 타깃(CHAT_ACTION_TARGETS)만 routeFromChatAction이 현재 화면 주소로 번역한다. 없어진 portfolio 타깃은 홈으로 흡수해서, 지난 답변이 그 타깃을 들고 와도 없는 화면으로 보내지 않는다.

4코드 소유권과 의존 규칙

계층별이 아니라 기능(F번호)별로 나눈다. 화면 본문은 전부 f0-home이 갖고, 기능 폴더에는 SPEC·계약·가드가 남는다.

강제되는 의존 방향

  • engine → types 만 import. LLM 호출·부수효과 금지
  • features → shared는 import 전용. 임시 타입·컴포넌트 복제 금지
  • Route Handler는 검증·전송만. OpenAI SDK를 직접 부르지 않는다
  • 엔진 지표마다 테스트 최소 1개

F11 피드에 화면이 없는 이유

전용 FeedScreen은 소비자가 없어 삭제됐다. 가족 기록은 지금 ArchiveScreen의 수익률(return) 탭 안에 있다. 그와 함께 shared/ui도 비었다 — 공용 React UI는 실제 소비자가 둘 이상 생길 때 다시 만든다.

발표가 장외 시간이거나 행사장 네트워크가 흔들려도 화면이 비면 안 된다.

8LLM 파이프라인 — F10 키웅이

모델은 gpt-5.6-luna 하나. F9 아카이브는 LLM을 쓰지 않는다 — 성향·수익률 숫자는 전부 shared/engine 순수 함수 결과다.

POST /api/chat                    ← Route Handler는 검증·SSE 전송만 한다
  │
  ├─ rate-limit  →  session  →  personal-data (Supabase 조회)
  │
  ├─ orchestrator : TypeScript 규칙 라우터   ← LangChain·LangGraph 미도입
  │     ├─ tools          읽기 전용 러너 (화면 값 조회)
  │     ├─ rewrite        "그럼 거기는?" 같은 지시어 질문 풀기
  │     │                 비스트리밍 1회 · reasoning none · 4초 타임아웃
  │     ├─ term-classify  용어 종류 분류 · structured output · reasoning low
  │     │                 └ 성공하면 승인된 고정 문장으로 답하고 자유 생성을 건너뛴다
  │     └─ 자유 생성      responses.create({ stream: true }) · reasoning low
  │                       델타를 서버 버퍼에 최대 4,000자 모은 뒤 3문장으로 자른다
  │
  ├─ 출력 검사 2단
  │     1단  shared/llm/filter        정규식·키워드 룰 · 전 출력 · 결정적
  │     2단  lib/output-judge         Luna 판정 · source === "model" 일 때만
  │
  └─ 통과한 완성 답변만 단일 text SSE 이벤트로 전송
     차단·타임아웃 → 고정 응답 (닫힌 실패)

왜 필터가 2단인가

1단만으로는 부족하다는 것이 실측으로 나왔다. 같은 의미를 다른 표현으로 쓴 추천·전망 문장 12개를 정규식 룰은 0/12 차단했고, 룰을 8개 늘려도 표현을 바꾼 5문장은 0/5였다. Luna 판정은 12/12·5/5를 차단하면서 정상 설명 8건은 0건 오탐했다. 단건 지연 약 1.5초는 SPEC의 "최소 2초 답변 준비" 카드 안에 들어간다.

2단을 아무 데나 돌리지 않는 이유 고정 응답·사전·FAQ·Tool 결과는 이미 승인된 텍스트다. 여기에 판정을 돌리면 비용과 지연만 늘고 판정기가 환각할 여지만 생긴다. 그래서 source === "model"인 자유 생성 답변에만 돌린다. 2단이 틀려도 1단이 잡던 표현은 그대로 막히므로 안전 하한선은 내려가지 않는다.
레드라인 (제품 규칙) 종목 추천 · 매매 시점 · 목표가 · 수익률 전망 · 훈계는 금지다. 수치 검증은 단위가 붙은 주장값만(123원·12%·10주) 화면 값과 대조하고, 1주당처럼 조사가 붙은 관용구나 단위 없는 설명용 숫자는 통과시킨다.

10개발 하네스 (앱 번들 밖)

6인이 Claude·Codex로 동시에 작업한다. 같은 파일을 두 세션이 만지는 사고를 시작 전에 차단한다.

한 작업 = 한 브랜치 = 한 worktree = 한 claim = 한 PR. 브랜치 이름은 {claude|codex}/{작업자}/{한글-작업명}이고 worktree 경로의 마지막 세 칸과 정확히 일치한다. 루트 main은 관제 전용이라 파일을 수정하지 않는다.

11알려진 부채와 어긋남

지금 코드를 읽는 사람이 헷갈릴 지점만 적는다. 숨기지 않는 것이 문서의 값어치다.

어긋남docs/기능명세.md에 없는 화면이 적혀 있다

기능명세 §2 트리와 §2.1 라우트 표는 /portfolio → PortfolioScreen이 있다고 적었지만, PortfolioScreen.tsx는 존재하지 않고 SCREEN_SEGMENTS에도 portfolio가 없다 — 지금 /portfolio는 404다. 코드(screen-route.ts:126)는 이미 챗봇의 portfolio 타깃을 홈으로 흡수하도록 고쳐졌고 문서만 안 따라왔다. 판단은 코드를 따른다.

부채컴포넌트 비대 · 인라인 스타일

OrderScreen.tsx 2,077줄 · ArchiveScreen.tsx 1,311줄. 계산은 lib/로 잘 뽑아냈지만 JSX가 안 쪼개졌다. 같은 뿌리로 f0-home 기준 className 5곳 대 인라인 hex 399곳이다 — 프로토타입 이관 정확도를 위해 의도한 부채이고 토큰화는 별도 작업이다. Tailwind v4 토큰을 실제로 쓰는 것은 F10 챗봇 UI뿐이다.

함정코드를 찾으러 가면 없는 폴더

shared/ui/는 .gitkeep뿐이고 f3-reason·f11-feed는 SPEC만 남았다. 의도된 상태지만 기능 ID가 폴더로 살아 있어 "여기 구현이 있겠지" 하고 찾아가게 만든다. behavior-demo/도 마찬가지로 현재 화면의 정본이 아니다.

미완가입 마법사에 서버 저장이 없다

SignupWizard는 부모 4단계·자녀 3단계 화면만 있고 저장 호출이 없다. 시연 계정은 마이그레이션 시드(seed_family_profiles)로 넣는다.
