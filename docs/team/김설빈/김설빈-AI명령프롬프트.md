# 김설빈 — AI 명령 프롬프트 가이드 (팀장 · 제안-승인 워크플로)

> 이 문서를 Claude/Codex에 그대로 복사·붙여넣기 해서 쓴다.

## 0. 사용법

1. 새 대화에서 §1 온보딩을 한 번 보낸다.
2. AI가 "읽었음"이라고 요약하면 §3에서 지금 할 작업 블록을 보낸다.
3. AI가 계획을 제시하면 이상 없을 때 "진행해"라고 한다.
4. 만들면 §5 자가검증을 보낸다.

## 1. 온보딩 프롬프트 (대화 시작 시 1회)

```
너는 "물려주는 계좌 — 영웅문 주니어"의 제안-승인 워크플로와 부모 화면 작업을 돕는다.
나는 김설빈, 팀장이자 실제투자 트랙 담당이다. 설명은 쉽고 명확하게.
먼저 아래 파일을 읽고 "읽었음"과 함께 ① 내가 할 일 ② 내가 하면 안 되는 것
③ 꼭 지킬 핵심 규칙을 정리해줘. 아직 만들지 마.
읽을 파일: 1.CLAUDE.md 2.docs/team/_공통_AI규칙.md(헌장) 3.docs/team/김설빈/김설빈-담당업무.md
4.web/AGENTS.md 5.물려주는계좌_기획안.md(3장·11장) 6.web/lib/rules.ts 7.web/lib/types.ts
환경: Next.js 16 + node:sqlite + 키움 REST(모의투자). 검증은 web 폴더에서
npm run typecheck / npm test / npm run verify. 작업 폴더: web/app/parent, web/app/api/proposals,
web/app/api/invite, web/lib/rules.ts, web/lib/kiwoom.ts.
```

## 2. 고정 규칙

```
[고정 규칙]
1. 반려 사유 입력은 서버가 422로 막는다. 프론트 검증만으로 끝내지 않는다(web/lib/rules.ts checkReason).
2. 안전장치는 web/lib/rules.ts에만 쓴다. 라우트는 rules를 호출만 한다 — 라우트에 규칙을 흩뿌리지 않는다.
3. web/lib/types.ts와 db.ts는 핫스팟이다. 바꿔야 하면 코드를 고치지 말고 "계약 변경 필요"라고 보고해라.
4. 승인 체결 전에 현재가·수량·예상 체결금액을 다시 확인받는 단계를 없애지 않는다.
5. 키움 API 상수는 추측하지 말고 키움 문서로 대조 확인한다. 모르면 "TODO: 확인 필요".
6. .env·API 키를 읽어서 출력하거나 커밋하지 않는다. 새 환경변수는 .env.example에만.
7. 한국어 파일은 편집도구/UTF-8로만. main 직접 push 금지(브랜치→PR).
```

## 3. 작업별 명령 프롬프트

### 3-1. 시연 시나리오 끊김 점검 (팀장 모드)

```
[작업] 기획안 11장의 시연 시나리오를 현재 코드로 처음부터 끝까지 따라가며, 어디서 끊기는지 찾아줘.
부모 배너 → 초대 → 아이 홈 → 예습 → 제안서 → 부모 반려+사유 → 아이 재제안 → 부모 승인 → 체결 → 아이 카드 상세.
[제약] 고치지 마라. 점검만.
[검증] 실제 코드 경로(라우트·화면 파일)를 근거로 제시. 없는 화면은 "미구현"으로 명시.
[산출물] 단계별 표: 구현됨 / 부분 / 미구현 + 담당 트랙 + 막힌 이유.
```

### 3-2. 반려 사유 필수 고정

```
[작업] 반려 시 사유 없이 요청하면 서버가 422로 막는지 확인하고, 안 막히면 막아줘.
[제약] 규칙은 web/lib/rules.ts에만. 라우트는 호출만.
[검증] web/scripts/verify.ts에 "사유 없는 반려는 422" 체크를 먼저 쓰고, 실제 요청을 보내
422가 나오는지 확인해줘. 공백 문자열·공백만 있는 문자열도 막히는지 같이 확인.
[산출물] 계획 먼저 → "진행해" 하면 구현.
```

### 3-3. 승인 → 키움 체결 연결

```
[작업] 부모 승인 시 현재가·수량·예상 체결금액을 재확인받고 키움 모의투자 주문까지 연결해줘.
[제약] web/lib/kiwoom.ts를 통해서만 호출한다. 상수·엔드포인트는 키움 문서로 대조하고
확인 못 한 값은 TODO로 남긴다. 실패 시 제안 상태를 어떻게 둘지 먼저 정하고 구현해라.
[검증] 모의투자 키로 실제 호출해서 결과를 보여줘. 키가 없으면 그 사실을 명시하고
호출 직전까지의 흐름만 테스트.
[산출물] 계획 먼저 → "진행해" 하면 구현.
```

## 4. 막히면 그대로 보내기

- 한 번에 하나: `지금은 [이것]만 하자. 다른 건 건드리지 마.`
- 규칙 위치 점검: `안전장치를 라우트에 직접 쓴 데 있어? 있으면 rules.ts로 옮겨줘.`
- 가짜 값 방지: `이 키움 상수 출처 있어? 추측이면 TODO로 바꿔줘.`

## 5. 자가검증 프롬프트 (PR 전)

```
방금 만든 걸 점검하고 표로 보고해줘 (실제로 실행/테스트해서):
1. 사유 없는 반려가 422로 막히나? (실제 요청 결과 붙여줘)
2. 안전장치가 rules.ts 밖에 흩어져 있나?
3. types.ts나 db.ts를 건드렸나? 건드렸으면 계약 변경으로 표시했나?
4. npm run typecheck / npm test / npm run verify 결과가 뭔가? (실행 결과 붙여줘)
5. 키·시크릿이 코드나 로그에 노출됐나?  6. 한국어 안 깨졌나?
아니오가 있으면 고친 뒤 다시 보고해.
```
