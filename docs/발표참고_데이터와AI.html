   │ 없음

AI 사용 여기가 기업정보 축에서 AI를 가장 크게 쓴 지점이다. 핵심 설계는 역할 분리와 정보 차단이다.

수집: 네이버 검색은 "후보 URL"만 찾고, 실제 기사 페이지에서 제목·시각·언론사·본문을 읽는다
  ▼

2거래 행동 로그 분석

"행동을 읽어 성향으로 돌려준다"의 실제 계산. 여기는 LLM을 한 번도 부르지 않는다.

2.1 수집하는 로그 3종

로그테이블담기는 값쓰이는 축
체결 + 질문식 기록 transactions side · 가격 · 수량 · trade_reason(매수 이유 6종) · plan_code(보유 계획 4종) · plan_target_price · plan_match(계획 준수 여부) · plan_changed_reason(변경 이유 5종) · realized_profit 정확력 · 집중력 · 분산력
탭 열람 stock_tab_views 종목별 카테고리(기업정보·차트·뉴스) 중 10초 이상 본 개수 근거력 · 직관력
주문 생애주기 orders (예약·취소·정산 RPC) 지정가 접수 · 취소 · 만기 정산 선제 도움 신호

전처리 결정 하나 — 체류 구간을 저장하지 않는다

초기 스키마는 opened_at·closed_at을 저장하고 서버가 duration_seconds를 생성 컬럼으로 계산했다. 지금은 프론트가 카테고리별 10초 이상 방문을 세어 종목당 최종 개수만 보낸다. 원시 타임스탬프를 안 남기니 저장량과 개인정보 노출이 줄고, 엔진이 필요로 하는 값은 그대로다.

마이그레이션: 20260814052538_stock_tab_views_per_stock_category_count.sql

일부러 안 받는 값 확신도·자신감 수치는 어떤 형태로도 저장하지 않는다. 아이가 스스로를 점수 매기게 하는 순간 "실력 채점"이 되고, 그건 레드라인(훈계 금지)에 걸린다. DB 제약 주석에도 명시돼 있다.

2.2 전처리 — 로그를 점수로 바꾸기 전에 하는 3가지

  1. KST 주 단위 버킷팅 — 체결 시각을 KST 날짜로 바꾸고 월요일 시작 주로 묶는다. 주차 카드는 그 주만이 아니라 그 주까지의 누적이다. 한 주만 자르면 표본이 2~3건이라 카드가 늘 "판정 보류"에 머물렀다.
  2. 과거 시점 포트폴리오 복원(replayPortfolio) — 현재 보유·현금에서 이후 거래를 최신순으로 되돌려 "그 주 마지막 날의 포트폴리오"를 다시 만든다. 집중력은 그 시점 기준이어야 하기 때문이다.
  3. 2거래일 뒤 종가 채점(gradeTrades) — 체결 다음 거래일부터 2거래일 뒤 종가와 비교. 매수는 오르면 적중, 매도는 내리면 적중. 2거래일이 안 지났거나 종가가 없으면 채점하지 않고 보류한다.

2.3 5축 산식

모든 축은 0~10이고 5가 중립이다. 표본이 없으면 5에서 시작하고 기록이 쌓일수록 5에서 멀어진다.

축정의산식
근거력사기 전에 자료를 봤는가 3탭 중 2개 이상을 매수 전에 10초 이상 본 매수의 비율 → 축소
직관력근거력의 보완쌍10 - 근거력
집중력한 곳에 몰아넣었는가 유효섹터수 = 1 / HHI → 10 - 5 × log₃(유효섹터수) → 현금 비중만큼 중립으로 당김
분산력집중력의 보완쌍10 - 집중력
정확력판단이 2거래일 뒤 맞았는가적중 비율 → 축소. 채점된 거래가 없으면 5

왜 HHI를 썼나 (질문 나오면 이걸로 답한다)

단순 "섹터 가짓수"로 세면:
   반도체 900만원 + 게임 1만원 = 섹터 2개 = "분산 투자했네"  ← 틀렸다

유효섹터수 = 1 / Σ(섹터비중²)  (허핀달 지수의 역수)
   위 경우 → 1.0 에 가깝다 = "사실상 한 곳에 몰빵"  ← 맞다

앵커: 유효섹터수 1 → 10점 / 3 → 5점(중립) / 9 → 0점. 로그 스케일이라 계단이 없다.
전량 현금이면 판단 근거가 없으므로 정확히 중립 5.

베이지안 축소 — 표본 1건으로 극단값을 못 내게

shrink(적중, 전체) = 10 × (적중 + k/2) / (전체 + k),  k = 4

"미리 2건 성공 · 2건 실패를 본 셈 친다"
→ 매수 1건 적중 시:  10 × (1+2)/(1+4) = 6.0    (단순 비율이면 10.0)
→ 표본 0건이면 정확히 5.0 (중립)

2.4 "모르면 모른다고 한다" — 판정 보류 규칙

2.6 이 축에 LLM을 안 쓴 이유

규칙 엔진 (채택)

  • 같은 입력 → 항상 같은 점수 (재현성)
  • "왜 6점이냐"에 산식으로 답할 수 있다
  • 테스트로 회귀를 잡는다
  • 호출 비용 0, 지연 0

  • 같은 아이에게 매번 다른 점수가 나올 수 있다
  • 부모가 근거를 물으면 설명 불가
  • 환각한 수치가 성장 기록으로 남는다
  • 금융 서비스에서 방어 불가

엔진 위치: web/shared/engine/behavior-profile.ts (546줄) + behavior-profile.test.ts (370줄)

LLM 미사용 축적 분석과 별개로, 지금 헤매는 순간을 룰로 잡아 챗봇이 먼저 말을 건다.

3AI 챗봇 "키웅이"

"챗봇 게이트를 어떻게 했는가" — 핵심은 생성을 최후 수단으로 미루는 구조다.

3.1 응답 우선순위 — 생성은 마지막이다

① 고정 사실 데이터   (승인 사전 · FAQ · 51종 종목 사실)        ← 전체 답변의 다수
② 화면 컨텍스트 계산 (지금 화면이 실제로 보여주는 수치)
③ 승인된 읽기 전용 조회 (본인 거래·성향·아카이브 툴 5종)
④ Luna 생성 1회      (①②③ 어디에도 안 걸릴 때만)
⑤ 전체 출력 게이트

★ 회사·제품·일상접점·섹터 역할 질문은 51종·13섹터 전부
  OpenAI 호출 없이 기본 답변이 가능해야 한다 (완료 기준)

600건 시뮬레이션에서 생성 후보(fallback)는 13.8%고, 실제 모델 경로까지 간 건 회귀 600건 중 2건이었다. 나머지 86%는 승인된 텍스트로 답한다.

단계판정실패 시
T0 요청·세션스키마 유효 · 세션 사용자 확정400 또는 로그인 안내
T1 입력 안전위기 → 개인정보 → 유해 → 추천 → 오프토픽 순서대로 분류상황별 고정 응답. 모델·툴 미호출

T5 출력 1단결정적 룰 — 금지 표현 정규식 · 단위 붙은 주장 수치 대조고정 안전 응답

T7 로깅경로·차단·조회·필터 결과 기록메트릭 장애가 권한을 넓히지 않음
설계에서 중요한 두 가지 ① 화이트리스트다. "나쁜 걸 막는다"가 아니라 "허용 목적 6종을 긍정 판정해야 통과"다. 목적을 못 정한 일반 대화·생활 질문은 모델에 보내지도 않는다.
② 원시 델타를 화면에 안 흘린다. 스트리밍 토큰을 그대로 뿌리면 검사 전 문장이 이미 아이 눈에 들어간다. 서버가 최대 4,000자 버퍼에 모은 뒤 완성문을 검증하고, 통과분만 단일 text 이벤트로 보낸다.

3.3 한 요청의 LLM 호출은 최대 4회 — 에이전트 루프를 안 만들었다

요청 → [T0·T1·T2 게이트] → 라우팅
                             │
      해석 실패 + 직전 답변 有 ├─→ ① 후속질문 재작성   reasoning none · 4초 · 200토큰
                             │      ("그럼 거기는 돈을 어떻게 벌어?" → 단독 질문으로)
                             │
      fallback 직전          ├─→ ② 용어 9종 분류      reasoning low  · 4초
                             │      성공하면 승인 고정문장으로 답하고 생성·판정 건너뜀
                             │      ↕ 배타적
      faq·context 고정답변   ├─→ ②' 답변 적합성 검사  reasoning low  · 4초
                             │
      위 분류가 none 이면    ├─→ ③ 답변 생성          reasoning low  · 8초 · 800토큰 · stream

      생성이 있었으면        └─→ ④ 출력 2단 판정      reasoning low  · 5초 · structured

★ 각 단계는 조건부 + 자체 타임아웃 + 닫힌 실패 처리
★ 대부분의 요청은 0~1회로 끝난다
★ 분당 12건 초과 시 429 + Retry-After (한 요청이 최대 4회를 부르므로 연타를 게이트 앞에서 끊는다)

왜 LangChain·LangGraph를 안 썼나 — 한 번 통과하는 파이프라인에 조건부 분기뿐이라 그래프 런타임의 이득보다 복잡도가 크다. 재검토 조건은 명시해뒀다: 한 요청에서 여러 툴의 반복 호출, 중단 후 재개, 사람 승인, 복잡한 재시도·분기가 실제 요구사항이 될 때.

3.4 출력 필터를 2단으로 만든 이유 — 실측 근거

정규식 1단만으로는 못 막는 게 있었다. 같은 의미를 다른 표현으로 쓴 문장이다.

검사기추천·전망 재표현 12문장룰 확장 후 재표현 5문장정상 설명 8건 오탐
1단 — 정규식 룰0 / 12 차단0 / 5 차단0
1단 — 룰 8개 확장일부0 / 5 차단0
2단 — Luna 판정12 / 12 차단5 / 5 차단0
  • 2단은 source === "model"인 답변에만 돈다. 고정 응답·사전·FAQ·툴 결과는 승인된 정적 텍스트라 호출하지 않는다 → 비용·지연이 거의 안 붙는다.
  • 인라인 판정이다. 먼저 보내고 뒤에서 검사하는 비동기는 안 쓴다 — 아이가 이미 읽은 뒤에 위반을 알아도 늦다. 단건 지연 약 1.5초는 최소 2초 "답변 준비 카드" 안에 들어간다.
  • 2단이 환각해도 안전 하한선은 안 내려간다. 1단이 잡던 표현은 그대로 차단된다.
  • 파싱 오류·시간 초과·호출 실패는 전부 닫힌 실패 → 고정 안전 응답.

수치 검증은 단위가 붙은 주장값만 대조한다(123원·12%·10주). 1주당처럼 조사가 붙은 관용구와 단위 없는 설명용 숫자는 화면 수치 주장이 아니므로 통과시킨다.

3.5 안전하지만 쓸모없는 답 — 적합성 검사

앞의 게이트가 못 잡는 실패 T0~T7은 전부 "나가는 문장이 위험한가"를 본다. 그런데 규칙 라우터는 낱말이 겹치면 승인된 카드를 낸다. 그래서 문장 자체는 늘 안전한 채 묻지 않은 것에 답하는 오답이 남는다. 이건 문장 형태로 구분되지 않아 정규식으로 못 잡는다 — 질문과 답을 함께 읽어야 판정된다.

의도별 실측 정확도를 재고, 낮은 쪽만 다시 읽게 했다.

의도정확도재검사
term 용어98%—
company 회사96%—
meta 챗봇 자신93%—
howto 사용법89%✓ 검사

mydata 내 기록23%✓ 검사

판정은 on/off 둘뿐. off면 승인 문장을 버리고 생성으로 돌려 T5·T5b를 받게 한다. 검사 실패는 승인 문장을 그대로 둔다(열린 실패) — 검사기가 죽었다고 안전한 답을 생성으로 바꾸지 않는다. 거절·안전·범위 밖 응답은 일부러 질문에 답하지 않는 것이라 검사 대상에서 제외한다.

3.6 DAPIE — 답을 주지 않고 되묻는 설명 대화

논문 기반 대화형 설명 구조(docs/DAPIE_논문_추출.md)를 승인 스크립트로 구현했다.

한 응답의 3부 구성:   피드백(머리말) → 개념 하나 설명 → 질문

정답 → 구체적 피드백 후 다음 행동을 묻는다
오답 → 정답을 바로 주지 않고 "더 쉬운 설명 · 더 작은 질문"으로 분기
       → 또 틀리면 예시와 함께 한 번만 다시 묻는다 (reaskCount 로 왕복 카운트)
       → 그 뒤에도 틀리면 정답 설명 + 비슷한 용어 카드 2장

★ LLM 은 단계 문구·선택지·정답을 생성하지도 해석하지도 않는다. 전부 승인된 정적 데이터.
★ 서버가 scriptId·stage·choiceId 를 등록 스크립트와 대조한다 — 위조한 전이는 거부.
★ 이해 여부를 평가하거나 점수화하지 않는다.

되물어서 답이 좁혀지는 질문이 아니면 되묻기가 오히려 방해다. 실제로 "차트는 어떻게 봐요?"에 "차트가 직접 보여주는 것은 무엇일까요?"로 되묻는 사고가 났다.

3.7 챗봇 지식 데이터 — 2티어로 나눈 기준

넣을 말을 고르는 기준은 하나 — 앱 화면이나 어린이 뉴스에 실제로 나오는 낱말. 자의적이지 않고, 텍스트로 검증 가능하고, 멈출 지점이 있다.

다루지 않는 상품도 사전에 넣었다

공매도·선물·파생·신용·공모주는 이 서비스가 안 다룬다. 그런데 아이는 유튜브에서 듣고 와서 묻는다. 모른 척하면 다른 데서 답을 찾고, 뜻만 알려주면 여기서도 되는 줄 안다. 그래서 한 답에 두 가지를 둔다 — ① 10~13세 눈높이 한 문장 뜻 ② "이 모의투자에서는 하지 않아요"라는 경계. 하는 방법은 설명하지 않는다. 경계 문장이 빠지면 테스트가 실패한다.

실제로 난 사고와 그 대응

두 글자 트리거가 낱말 중간에 걸렸다. 조회를 공백 지운 문자열로 하니 경계가 사라져 "공시가 뭐야?" → 시가로, "수주잔고가" → 고가로 답했다. 이제 원문을 함께 넘겨 앞 글자가 한글이면 버린다. 라우터가 이 인자를 빼면 사고가 되살아나고 테스트가 잡는다.

5예상 질문 대응

Q. LLM이 환각하면 어떡하나?

세 겹으로 막습니다. ① 애초에 답변의 86%가 승인된 정적 텍스트라 생성 자체가 안 일어납니다. ② 생성된 답변은 결정적 정규식 1단과 Luna 판정 2단을 인라인으로 통과해야 화면에 나갑니다. ③ 수치는 화면 컨텍스트 허용 목록과 대조합니다 — 모델이 새 숫자를 만들면 그건 버그이고 차단됩니다. 그리고 실패는 전부 닫힌 실패입니다. 판정이 시간 초과되면 통과가 아니라 고정 응답으로 내려갑니다.

Q. 성향 점수를 AI가 만드나?

아닙니다. 5축·4캐릭터는 전부 순수 함수 규칙 엔진이 계산합니다(shared/engine/behavior-profile.ts). HHI 역수로 유효 섹터수를 내고 베이지안 축소를 적용합니다. LLM은 그 결과 JSON을 읽어 쉽게 설명만 합니다. 표본이 부족하면 캐릭터를 확정하지 않고 "관찰 중"으로 둡니다.

Q. 아이가 "뭐 사면 돼?"라고 물으면?

정규식 정확 일치가 아니라 정규화한 자연어의 의미 단서 조합으로 판정합니다. "떡상", "존버", "낼 오를까", "찍어줘" 같은 구어체가 달라도 취지가 같으면 같이 차단됩니다. 그리고 거절로 끝내지 않고 고정 대안 질문을 냅니다 — 종목 선택 요구에는 회사 소개·수익 구조를, 가격 예측에는 차트와 변동성의 의미를 내밉니다. 600건 중 추천 의도 122건이 121건 refusal로 갔습니다.

Q. 부모가 아이 대화를 볼 수 있나?

없습니다. 대화 원문과 행동 데이터는 부모에게 전달하지 않고, F10 로그는 성향 스코어링에도 반영하지 않습니다. 조회 대상 사용자는 서버가 HttpOnly 쿠키에서만 정합니다 — 클라이언트도 모델도 조회 대상을 지정할 수 없습니다. 가족 구성원의 기록 접근 시도는 거부하고 테스트로 검증합니다.

Q. 왜 에이전트 프레임워크를 안 썼나?

한 번 통과하는 파이프라인에 조건부 분기뿐이라 그래프 런타임을 얹을 이득보다 복잡도가 큽니다. Next.js 단일 TypeScript 서비스에 Python 런타임을 더할 이유도 없었습니다. 재검토 조건은 문서에 적어뒀습니다 — 한 요청에서 여러 툴 반복 호출, 중단 후 재개, 사람 승인, 복잡한 재시도·분기가 실제 요구사항이 될 때 LangGraph를 다시 봅니다.

Q. 시연 중에 API가 죽으면?

시세는 키움 → Supabase 보관 캔들 → 코드 픽스처 3단 폴백이고, LLM이 죽으면 사전·FAQ 전용 모드로 강등합니다. 챗봇의 모든 LLM 단계가 자체 타임아웃(4~8초)과 고정 응답 폴백을 갖고 있어서, 어느 단계가 실패해도 대화는 계속됩니다.

6아직 안 된 것 — 먼저 말하는 편이 낫다

심사위원이 찾아내기 전에 먼저 꺼내면 신뢰가 오른다. 아래는 문서에 [제약]·[가정]으로 표기된 것들이다.

항목현재 상태
