## 0. 전제 (중요 — 이전 판에서 변경됨)

| 항목 | 결정 |
|---|---|
| 영웅문 실제 임베드 | **하지 않는다.** 시연 목적이므로 키움 앱에 직접 넣을 수 없다 |
| 제품 컨셉 | **"자녀용 영웅문"을 우리가 만든다.** 자녀가 쓰는 MTS 셸 안에 게임·도감/뉴스·제안서가 들어간다 |

## 2. 배포 형태 — 웹 확정

### 2.1 근거

**(1) 시연 우위가 비대칭이다.** 웹으로 만들면 앱도 가지지만(Capacitor), 앱으로 만들면 웹은 못 가진다.

| 시연 항목 | 웹 | 네이티브 |
|---|---|---|
| 발표 화면에 띄우기 | 브라우저 열면 끝 | 브라우저 불가. 에뮬레이터/기기 미러링 필요 |
| **PvP 양측 동시 시연** | 일반창 + 시크릿창으로 한 노트북에서 | 기기 2대 동시 미러링 |
| 관객 QR 체험 | 스캔 → **3초** → 플레이 | 스토어/APK 설치 40초~3분, 현장 와이파이에서 실패 다발 |
| 배포 반영 | 즉시 | 재빌드·재설치 |

**(2) 진입점이 두 개다.** 자녀(앱/PWA)와 부모(부모 뷰)의 정보구조가 다르지만, 시연에서 브라우저 2창으로 띄우려면 **같은 도메인·같은 배포**가 압도적으로 편하다. → 단일 Next.js에 route group으로 분기(§3).

**(3) Capacitor는 마지막에 붙인다.** 같은 웹 빌드를 감싸는 구조라 재작업이 없다. 자녀에게 "앱을 깐다"는 경험과 네이티브 푸시가 필요해지는 시점에만 착수한다.

### 2.2 Capacitor로 얻는 것 / 못 얻는 것

| 얻음 | 못 얻음 |
|---|---|
| 스토어 배포, 앱 아이콘, 스플래시 | 앱 시작 속도 (WebView 초기 로딩 1~2초) |
| 네이티브 푸시 — iOS 웹푸시 제약 해소 | 고성능 3D·파티클 (본 게임엔 불필요) |
| 생체인증, 보안 스토리지, 햅틱 | 위젯·백그라운드 실행 (불필요) |
| 콘텐츠는 심사 없이 웹에서 즉시 갱신 | 순정 네이티브 제스처 감각 |

푸시가 필요한 이유는 제품 핵심 루프다: *자녀가 제안서 전송 → 부모 알림 → 부모 승인 → 자녀 알림.*

## 3. 프로젝트 구조

> **결정 (2026-08-06)**: `apps/` + `packages/` 모노레포로 재편하는 안 대신 **팀 기존 배치(`game/` + `web/`)를 유지**한다.
> `team-git-policy.md`의 담당 경계·핫스팟이 폴더 기준으로 이미 서 있고, AGENTS.md의 검증 명령
> (`cd game; npm test`)이 그대로 살기 때문이다. 룰 엔진 공유는 **npm workspaces**로 해결한다.

### 3.1 루트

```
six-opening/
├─ package.json             { "workspaces": ["game", "web"] }
│
├─ game/                    ── 게임 트랙 ──
│  ├─ src/                  룰 엔진 (순수 TS, SSOT) — web·server·sim이 공유
│  ├─ data/                 카드풀 + 이벤트×섹터 매트릭스 (밸런스 시트)
│  ├─ server/               Colyseus PvP — 권위 판정
│  ├─ sim/                  밸런스 시뮬레이터 CLI
│  └─ tests/                Vitest
│
├─ web/                     ── Next.js 자녀 영웅문 + 부모 뷰 ──
│  ├─ app/                  라우팅과 조립만
│  ├─ features/             도메인 단위 (game portfolio proposal dex news)
│  ├─ components/ui/        도메인 모르는 표현 컴포넌트
│  └─ lib/brokerage/        증권 어댑터 — port + mock
│
├─ content/                 도감 · 뉴스 MDX (편집 콘텐츠)
├─ pipelines/               Python(uv) — 종가 스냅샷, 뉴스 LLM 요약
└─ docs/
```

**경계의 근거**

| 위치 | 왜 여기인가 |
|---|---|
| `game/src` | **구조의 핵심.** 클라(즉시 UI 반응)와 서버(권위)가 같은 판정을 돌려야 한다. 구현이 갈리면 "클라는 낼 수 있다는데 서버가 거부" 버그가 상시 발생 |
| `game/data` | 밸런스 튜닝은 *데이터만* 바꾸는 작업이다. 로직과 섞이면 시뮬레이터가 여러 데이터셋을 못 돌린다. Python 파이프라인이 가격을 갱신하는 지점이기도 하다 |
| `game/server` | 같은 폴더에 두어 담당 경계를 유지한다. `web`에 colyseus 의존이 새지 않도록 package.json `exports`로 진입점을 분리 |
| `web/lib/brokerage` | 소비자가 web뿐이다. 별도 패키지로 뽑으면 불필요한 추상화 |

> 공용 UI 패키지는 만들지 않는다. 소비자가 `web` 하나뿐이라 현 시점에선 과한 분리다.

**npm workspaces를 쓰는 이유**: `web`이 `import { reduce } from 'game'`으로 룰 엔진을 직접 쓴다.
빌드 산출물(dist)을 거치지 않으므로 룰을 한 줄 고치면 web에 즉시 반영된다.
pnpm/Turborepo는 도입하지 않았다 — 워크스페이스가 2개뿐이라 npm 내장 기능으로 충분하다.

### 3.2 `web/`

```
web/
├─ app/
│  ├─ (child)/                      ── 자녀 영웅문 ──
│  │  ├─ layout.tsx                 MTS 셸 (하단 탭바: 홈·게임·도감·제안)
│  │  ├─ home/page.tsx              계좌 홈 — 총자산·보유종목·수익률 (mock 실계좌)
│  │  ├─ stock/[code]/page.tsx      종목 상세 — 차트·기업정보·"부모님께 제안" CTA
│  │  ├─ game/
│  │  │  ├─ page.tsx                로비 · 매칭
│  │  │  ├─ deck/page.tsx           덱 편집 (30장, 동일종류 최대 5)
│  │  │  └─ [roomId]/page.tsx       대전 화면

│  │  └─ proposal/
│  │     ├─ new/page.tsx            제안서 작성
│  │     └─ [id]/page.tsx           제안 상태 (대기·승인·반려)
│  │
│  ├─ (parent)/                     ── 부모 뷰 ──
│  │  ├─ layout.tsx
│  │  ├─ inbox/page.tsx             제안서 수신 · 승인/반려
│  │  ├─ child/[childId]/page.tsx   자녀 활동 리포트 (게임 성적 · 학습 진도)
│  │  └─ onboarding/page.tsx        자녀 프로필 생성 · 초대코드 발급
│  │
│  ├─ (public)/
│  │  ├─ invite/[code]/page.tsx     초대코드 진입
│  │  └─ p/[shareId]/page.tsx       제안서 공유링크 — **OG 메타 필요(SSR)**
│  │
│  ├─ api/                          route handlers
│  ├─ layout.tsx
│  └─ globals.css
│
├─ features/                        도메인 단위로 컴포넌트 + 훅 + 스토어를 묶는다
```

### 3.3 `game/` — 룰 엔진 SSOT

```
game/
├─ src/
│  ├─ types.ts          공용 타입 (섹터·카드·GameState·Action)
│  ├─ rules.ts          룰 상수 — 밸런스 조정은 여기부터
│  ├─ rng.ts            결정적 난수 (시드 재현)
│  ├─ state.ts          createInitialState — 자금·덱·패·필드
│  ├─ pricing.ts        현재가 = 시작가 × ∏(1 + 효과ᵢ)
│  ├─ hand.ts           패 5종류 유지 규칙
│  ├─ domain.ts         영역 전개 — 이벤트×섹터 매트릭스 적용 (Q4·Q5)
│  ├─ deck.ts           덱 검증 (30장 · 동일종류 5장)
│  ├─ settle.ts         총자산 원화 환산 정산
│  ├─ actions/
│  │  ├─ buy.ts  sell.ts  exchange.ts   매수 · 매도 · 환전
│  │  ├─ skill.ts  hedge.ts             스킬(Q1) · 회피(Q2, 미구현)
│  │  ├─ swapDeck.ts                    패↔덱 종류 교체 (Q7)
│  │  ├─ endTurn.ts                     턴·라운드 전환 + 영역 전개
│  │  └─ index.ts       reduce() ← 클라·서버 공용 유일 진입점
│  └─ index.ts
├─ data/                cards.ts · events.ts · decks.ts
├─ server/              GameRoom.ts (Colyseus) · index.ts
├─ sim/                 밸런스 시뮬레이터 CLI
└─ tests/               Vitest
```

**I/O 의존을 넣지 않는다.** 순수 함수 집합으로 유지하면 서버·UI 없이 단독 시뮬레이션이 가능해지고, 매트릭스(기획서 v0.3: 환경 7 × 섹터 7)·운 보정 밸런스를 수치로 검증할 수 있다.

`reduce(state, action)`은 입력을 변형하지 않고 사본에 적용한다. 클라는 UI를 즉시 반응시키려고 미리 돌리고, 서버는 같은 함수로 최종 판정을 낸다.

> **모듈 해석 주의**: `game`은 상대 import에 확장자를 쓰지 않고 `moduleResolution: Bundler`로 해석한다.
> Turbopack이 NodeNext 스타일의 `'./x.js'` 표기를 `.ts`로 되돌려 찾지 못하기 때문이다.
> 대신 `game`은 tsx/vitest/번들러 없이 순수 node로 실행할 수 없다.

### 3.4 `web/lib/brokerage` — Mock 증권 레이어

```
web/lib/brokerage/
├─ types.ts          Account, AccountHolding, Proposal
├─ port.ts           interface BrokeragePort  ← 유일한 경계
├─ mock/
│  ├─ adapter.ts     시연용 구현 (메모리)
│  └─ fixtures.ts    자녀 계좌 시드 (보유종목·평가손익)
└─ kiwoom/           실연동 자리
```

> `BrokeragePort`에 `placeOrder`를 추가하지 않는다. 앱이 주문을 내는 순간 (b) 범위를 벗어나고,
> 앱이 종목을 권유하는 구조가 되어 투자권유 규제에 걸린다(§9). 인터페이스가 곧 제약이다.

시연에서는 mock이 (b) 시나리오를 그대로 재현한다: 자녀 화면에 실계좌처럼 잔고·보유종목·수익률이 뜨고, 주문 버튼은 **제안서 전송**으로 연결된다. 실주문 API는 호출되지 않는다.

발표 시 설명 포인트: *"증권 연동은 포트 하나로 추상화돼 있고, 키움 어댑터를 구현하면 화면 변경 없이 실계좌로 전환됩니다."*

### 3.5 `content/` · `pipelines/`

```
content/
├─ dex/*.mdx            도감 문서
└─ news/*.mdx           뉴스

pipelines/              Python (uv)
├─ close_snapshot/      일 1회 종가 → game/data 카드 가격 갱신
└─ news_digest/         이슈 → Claude API 재작성 → 사람 검수 → 발행
```

CMS는 도입하지 않는다. 카드 30~50종 규모에서는 Git이 곧 버전관리·리뷰·롤백이다.

## 4. 게임 렌더링 — DOM

| 옵션 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **React DOM + Framer Motion** | 카드 내 한글 텍스트(기업설명·키워드 3개) 렌더 자유, 나머지 화면과 스택 통일, 저사양 WebView 안전, 번들 작음 | 대량 파티클 한계 | **채택** |
| Pixi.js / Phaser | 이펙트 자유도 | 카드 텍스트 레이아웃 비용 큼, WebGL 미지원 기기 리스크, 번들 +300KB~ | 특정 씬 오버레이로만 |
| Unity / Cocos WebGL | 연출 최상 | 번들 수십 MB → 초기 로딩 치명적, 이중 스택 | **탈락** |

동시에 움직이는 요소는 패 5 + 자기 필드 3 + 상대 필드 3 수준이다. "영역 전개" 연출은 **Lottie 1개 + CSS**로 처리한다.

> **성능 리스크**: 타깃이 초등 고학년이므로 실제 주력 기기는 *부모에게 물려받은 3~5년 된 저가 안드로이드*일 가능성이 높다. 프로토 단계에서 저사양 실기기 1대로 반드시 측정한다. (추측 금지 항목)

| **Next.js App Router** | **채택.** 도감/뉴스는 SSR/ISR이 적합하고, 결정적으로 **제안서 공유 링크에 OG 미리보기가 필요** — CSR로는 불가 |
| Vite + React SPA | 게임만 보면 더 가벼움. 도감/뉴스/공유링크에서 손해 |
| SvelteKit / Nuxt | 성능 우위 미미, 생태계·인력 손해 |

## 6. 게임 서버

| 옵션 | 장점 | 단점 |
|---|---|---|

### 6.1 네트워크 주의사항

- 턴제이므로 저지연 요구 없음. WebSocket으로 충분, 롤백 넷코드 불필요
- **WebView 백그라운드 전환 시 소켓 절단**이 실사용 최대 이슈 → 재접속 + 상태 재동기화를 처음부터 설계에 포함
- Colyseus는 stateful 롱커넥션 → **Vercel serverless 배포 불가.** Fly.io / Railway 별도 배포

## 7. 인증 · 개인정보

### 7.1 법적 제약

**만 14세 미만 개인정보 수집은 법정대리인 동의 필수(개인정보보호법 §22-2).** 타겟이 초등 고학년이므로 정면으로 해당한다. 자녀가 스스로 계정을 만드는 플로우는 채택하지 않는다.

```
부모  → 자녀 프로필 생성 + 법정대리인 동의
      → 초대코드 발급
자녀  → 코드 입력 → 닉네임만 입력 → 시작
```

**자녀에게서 이메일·전화번호를 수집하지 않는다.** 저장 항목은 닉네임 + 부모 계정 FK뿐이다. 수집하지 않으면 보호할 대상도 없다. 시연에서도 이 플로우를 그대로 보여준다 — 규제 대응이 곧 데모 포인트다.

### 7.2 시연 범위

키움 SSO는 사용하지 않는다. Supabase Auth(부모: 이메일 매직링크 / 자녀: 초대코드 기반 세션)로 충분하다.

### 7.3 자녀 실계좌 연동 = (b)

| 단계 | 내용 | 본 프로젝트 |
|---|---|---|
| (a) 자녀가 직접 로그인·주문 | — | ❌ 미성년자 본인인증 수단 부재, 미성년 계좌는 법정대리인 거래가 원칙 |
| **(b) 자녀는 조회·제안, 주문은 부모** | 자녀 명의 계좌 | ✅ **채택 — 화면으로 구현, 데이터는 mock** |
| (c) 계좌 없음, 게임·모의만 | — | 미채택 |

## 8. 증권 데이터

시연 단계에서는 외부 API를 호출하지 않는다.

```
[시연]  game/data 고정 스냅샷  →  brokerage/mock  →  화면
[실서비스]  키움 API  →  brokerage/kiwoom  →  (화면 변경 없음)
```

- 게임 시작 시 종목 가격을 **세션에 고정 스냅샷으로 복사**한다. 진행 중 외부 변동이 판정에 끼어들지 않게 한다
- 실서비스 전환 시에도 "전일 종가"만 쓰는 기획서 §8의 설계를 유지한다. 실시간 시세 재배포는 KRX/NASDAQ 라이선스 계약 대상이지만 종가 스냅샷은 부담이 현저히 낮다

## 9. 콘텐츠 정책

**뉴스**
- 원문 크롤링·전재 금지 (저작권)
- 실제 이슈 → Claude API로 아이 눈높이 재작성 → **사람 검수** → 발행
- 아동 대상이므로 **자동 발행 금지.** 검수 단계를 파이프라인에서 생략 가능하게 만들지 않는다

**제안서**
- 범위: 자녀 제안 → 부모 확인 → (실서비스에선) 부모가 직접 주문
- **앱이 종목을 추천하는 구조로 만들면 투자권유 규제에 저촉된다.** 추천 주체는 항상 **자녀**이며, 앱은 자녀의 의견을 전달하는 통로에 머문다
