1치명 — 자산·랭킹 무결성

셋 다 "서버가 클라이언트를 믿는다"는 같은 뿌리다. 가족 랭킹·수익률 트랙·F9 성향 카드가 전부 이 값을 읽으므로, 하나가 뚫리면 리그 전체가 오염된다.

1. 체결가를 클라이언트가 정한다 — 서버·DB 어디에도 시세 대조가 없다 치명 코드확인

증상
매수·매도 체결가가 브라우저가 보낸 price 그대로 DB에 들어간다. 현재 시세와 대조하는 코드가 서버에도 DB 함수에도 없다.
경로
OrderScreen.tsx:1084이 화면의 price를 그대로 실어 보내고 → app/api/trade/route.ts:104는 positiveNumber()(0보다 큰 유한수)만 검사하고 → apply_trade(20260815033308_order_lifecycle_db_ownership.sql)도 p_price <= 0만 막는다.
재현
# 1) 헐값에 대량 매수
POST /api/trade
{"side":"buy","stock_code":"005930","price":1,"quantity":9000000}
→ 900만원으로 삼성전자 900만주 보유

# 2) 실제 시세로 매도 → 무한 수익
POST /api/trade
{"side":"sell","stock_code":"005930","price":78000,"quantity":9000000}
영향
가족 랭킹, 아카이브 수익률 탭의 달리기 트랙, GET /api/family의 구성원 수익률, F9 성향 카드의 정확 축이 모두 transactions를 원본으로 읽는다. 리그의 존재 이유가 무너진다.
조치
서버가 getQuote(stock_code)를 다시 읽어 체결가를 서버 값으로 덮거나, 최소한 허용 괴리(예: ±3%)를 벗어나면 invalid_amount로 거절한다. 클라이언트 price는 표시용으로만 받는다.

2. DEMO_USER_ID=1 폴백으로 비로그인 API가 열려 있다 치명 코드확인

증상
쿠키가 아예 없는 요청은 DEMO_USER_ID 사용자로 처리된다. 저장소 루트 .env:19에 DEMO_USER_ID=1(김찬영)이 실제로 들어 있다.
경로
app/api/supabase.ts:180. 바로 위 주석은 "화면은 로그인인데 API만 열려 있으면 안 된다"고 적었지만, 그 방어는 낡은 쿠키를 들고 온 경우만 막는다(if (raw) return sessionUserIdFromCookie(raw)). 쿠키가 없으면 그 분기 자체를 지나간다.
재현
# 쿠키 없이
GET  /api/account    → 자녀 잔액·보유 노출
GET  /api/trades     → 매매 기록·이유 노출
POST /api/trade      → user 1 명의로 체결
POST /api/chat       → 자녀 개인 데이터 툴 실행
영향
page.tsx는 폴백 없는 sessionUserIdFromCookie를 쓰므로 화면만 로그인 게이트로 잠긴다. 시연을 Cloudflare 터널로 외부 공개하는 구조라 주소를 아는 사람이면 누구나 닿는다. 1번과 결합하면 외부인이 자녀 계좌를 임의로 조작할 수 있다.
조치
NODE_ENV === "production"에서는 DEMO_USER_ID를 읽지 않는다. 또는 .env에서 지우고 개발용 로그인으로 대체한다.

3. 예약 체결일(scheduled_for)에 과거 날짜 검증이 없다 치명 코드확인

증상
장외 시장가 예약의 체결 예정일을 클라이언트가 정하는데, 서버는 typeof === "string"만 본다.
경로
app/api/orders/route.ts:166에서 무검증 통과 → 정산기 scheduled-orders.js의 findConfirmedOpeningCandle은 scheduledFor 이후 가장 이른 확정 일봉을 고른다(.sort((l,r) => l.time - r.time)[0]).
재현
POST /api/orders
{"order_type":"market","side":"buy","stock_code":"005930",
 "scheduled_for":"2026-01-02","reserved_amount":10000000,
 "request_mode":"amount"}

# 다음 GET /api/orders 가 정산을 겸하므로 화면만 한 번 열면
→ 2026-01-02 이후 첫 거래일 시가로 체결된다
영향
보관 캔들 범위(chartRetentionCutoff) 안에서 가장 유리한 시가를 골라잡을 수 있다. 1번보다 은밀하다 — 체결가가 실제로 존재했던 가격이라 기록만 봐서는 이상해 보이지 않는다.
조치
scheduled_for를 서버가 nextOpeningDate()로 직접 계산한다. 클라이언트 값을 받아야 한다면 >= 오늘(KST)을 강제한다. 1번을 고칠 때 한 줄로 같이 끝난다.

2높음 — 시연 중 실제로 터질 것

악의가 없어도 나온다. 4·5·6번은 발표 당일 무대에서 그대로 보일 수 있다.

4. 공휴일에 "즉시 체결"이 된다 — 휴장일 판정이 없다 높음 코드확인

증상
isRegularMarketOpen이 요일과 시각만 본다. 평일 공휴일을 정규장으로 판단해 직전 영업일 종가로 즉시 체결한다.
근거
f2-trade/lib/scheduled-orders.js — day >= 1 && day <= 5 && minute >= 540 && minute < 930. 저장소 전체에서 휴장·holiday·공휴일을 검색하면 챗봇 용어 사전의 답변 문구 하나만 나온다("휴장은 주식시장이 문을 열지 않는 날이에요"). 즉 챗봇은 휴장을 설명하는데 앱은 휴장을 모른다.
파생
nextOpeningDate도 주말만 건너뛰므로 예약 체결일이 공휴일로 잡힌다. 이쪽은 findConfirmedOpeningCandle이 거래량 있는 봉만 고르므로 자동으로 다음 영업일로 밀린다 — 즉시 체결 경로만 위험하다.
조치
KRX 휴장일 상수 배열(연 15일 남짓)을 scheduled-orders.js에 두고 isRegularMarketOpen·nextOpeningDate·isWeekdayKey가 함께 본다. 배열 하나로 끝난다.

5. 51장 중 한 종목만 live면 화면 전체가 "실시간"이 된다 높음 재현필요

증상
유니버스 응답의 source가 live인 조건이 51종 중 하나라도 live다. 나머지 50장은 전일 종가 또는 픽스처인데 같은 화면에 섞여 나온다.
근거
app/api/universe/service.ts:170 — const live = Object.values(warmQuotes).find(q => q.source === "live"). 키움 어댑터는 초당 1건 큐(REQUEST_INTERVAL_MS = 2600)에 한 폴링당 한 종목만 데운다(providers/kiwoom.ts 주석: "카드 51장을 초당 1건으로 다 데우려면 2분이 넘는다").
영향
탐색 화면의 기본 정렬이 "오늘 많이 오른 순"이다. 워밍업 구간에서는 이 순위가 실시간 등락률과 전일 종가 기준 등락률을 섞어 매긴다. 시연 시작 직후 2분이 정확히 그 구간이고, 그때가 심사위원이 탐색 화면을 처음 보는 순간이다.
조치
단기 — local-demo.ps1에 워밍업 대기를 넣어 시연 전에 51종을 다 채운다. 근본 — source를 종목별로 화면에 내려 정렬에서 미확인 종목을 뒤로 보내거나, 헤더 라벨을 live n/51로 바꾼다.

6. 시세 폴백이 나이 제한 없는 stale·픽스처를 실체결로 흘린다 높음 코드확인

증상
제공자 조회가 전부 실패하면 anyCached()가 신선도와 무관하게 남은 값을 돌려주고, 그것도 없으면 코드 픽스처를 돌려준다. 사용자는 가짜 가격인 줄 모른 채 그 가격으로 실제 체결한다.
근거
app/api/quote/quotes.ts:173 anyCached(quoteCache, symbol)?.value ?? fixtureQuote(fixture). 폴백 사다리 자체는 잘 설계돼 있고 source 필드도 정확히 실린다 — 문제는 그 필드를 그리는 화면이 없다는 것이다(source === "fixture" 참조는 universe/service.ts 내부에서만 발견).
영향
발표 중 시세 API가 죽어도 화면이 멀쩡해 보이는 것은 설계 의도(강점)지만, 그 상태에서 이뤄진 체결이 진짜 거래 기록으로 남아 아카이브·랭킹에 들어간다. "발표 중 죽지 않는다"와 "가짜 가격으로 자산이 바뀐다"는 다른 문제다.
조치
주문 화면에 source !== "live"일 때 배지 한 줄("지금은 참고 시세예요"). 체결 자체를 막을지는 제품 결정 — 데모에서는 막지 않는 편이 낫다.

7. 챗봇 수치 게이트가 클라이언트 신고값을 화이트리스트로 쓴다 높음 재현필요

증상
출력 게이트의 unverified_number 검사는 "허용 목록에 없는 수치를 말하면 폐기"다. 그런데 그 허용 목록이 요청 본문의 context에서 온다.
근거
f10-chatbot/lib/orchestrator.ts:761 allowedNumbers: allowedContextNumbers(request). contracts.ts는 범위만 검사한다 — MAX_CASH = 1_000_000_000_000, MAX_UNIT_PRICE = 1_000_000_000, MAX_PNL_PERCENT = 100_000. 서버 계좌와 대조하지 않는다.
영향
"수치는 LLM이 아니라 서버 도구 값만 사용한다"는 F10 레드라인이 클라이언트가 정직할 때만 성립한다. 위조된 context로 키웅이가 임의 손익률을 말하게 만들 수 있다. 실제 아이가 할 일은 아니지만, AIX 심사에서 "게이트를 어디서 검증하나"를 물으면 정면으로 걸리는 자리다.
조치
allowedContextNumbers가 이미 서버에 있는 createSupabasePersonalData 값을 함께 쓰도록 합친다. 최소한 현금·손익만이라도 서버 값으로 교체.

8. lastAnswer 800자가 검증 없이 모델로 되돌아간다 높음 재현필요

증상
지시어 해소(재작성)용으로 받는 lastAnswer가 실제로 서버가 보낸 답인지 확인되지 않는다.
근거
f10-chatbot/lib/contracts.ts:37 MAX_PREVIOUS_ANSWER_LENGTH = 800. 타입 주석은 "아이가 쓴 말은 담지 않으므로 입력 게이트를 통과한 적 없는 텍스트가 모델로 되돌아가지 않는다"고 적었는데, 그 보장은 클라이언트가 규약을 지킬 때만 참이다. 서명·해시·서버 세션 대조가 없다.
영향
출력 게이트가 최종 방어선이라 피해는 제한적이다. 다만 questions-v4(적대적 우회 34건)는 사용자 메시지 축만 본다 — 컨텍스트 필드를 통한 주입 축이 회귀 세트에 없다.
조치
회귀 세트에 컨텍스트 주입 케이스를 추가하는 것이 먼저다. 코드는 lastAnswer를 서버 세션에 잠깐 보관하고 클라이언트에게서 받지 않는 쪽이 정석이지만, 지금 구조(무상태)에서는 비용이 크다.

10. Supabase가 한 번 흔들리면 부모가 자녀용 답변을 받는다 중간 코드확인

증상
loadSessionProfile이 예외를 삼키고 null을 준다(app/api/chat/route.ts:60) → resolveChatSession(null)은 데모 세션으로 낮춰 잡고 역할이 항상 child다.
영향
f10-chatbot/lib/role-copy.ts의 tradingLock 분기가 뒤집혀 부모에게 자녀용 문구·버튼이 나간다. 로그에는 sessionSource로 남지만 화면은 조용하다. 폴백 방향 자체는 안전한 쪽(자녀 기준이 더 보수적)이라 설계 판단으로 볼 여지가 있으나, 부모 시연 중 한 번 흔들리면 그대로 보인다.
조치
프로필 조회 실패를 답변 차단 사유로 올리지는 말되, 역할 의존 문구(role-copy)만은 unknown 분기를 따로 둔다.

11. PostgREST 필터에 형식 미검증 문자열이 들어간다 중간 재현필요

증상
app/api/feed/access.ts:88 id: `in.(${ids.join(",")})`. 검증자 isTransactionId는 "빈 값 아님 + 64자 이하"만 본다. 실제 값은 UUID인데 )·"·* 같은 PostgREST 문법 문자를 그대로 통과시킨다.
영향
같은 패턴이 authorizeFeedTarget의 id: eq.${transactionId}, comments/route.ts:88의 in.(...)에도 있다. 대부분 PostgREST가 400을 내 502로 끝날 가능성이 높지만, 가족 범위 스코프를 우회하는 필터를 만들 수 있는지는 실제로 쏴 봐야 안다.
조치
isTransactionId를 UUID 정규식으로 좁힌다. 한 줄이고 부작용이 없다.

12. 코멘트 필터가 자기 안내 문구와 모순된다 중간 코드확인

증상
추천 차단 메시지가 "왜 그렇게 생각했는지 물어보는 건 어떨까요?"인데, shared/engine/comment-filter.ts의 /(왜그랬어|왜샀어|왜팔았어)/가 그 말을 scolding으로 차단한다. 안내대로 따라 쓰면 또 막힌다.
파생 오탐
normalize()가 공백·문장부호를 전부 지우고 매칭하므로 (한심|답답|바보|멍청|어이없|실망이)에 "실망이 아니라 자랑스러워"가 걸린다. (못했|잘못했|틀렸어|실패했|망했)도 "실패했어도 괜찮아"를 막는다.
영향
F11의 목적이 "대화 거리를 만든다"인데 필터가 대화를 막는다. 필터의 의도(데이터 무결성)는 옳고 구현이 과차단이다.
조치
왜샀어 계열을 scolding에서 빼거나 왜샀어대체 같은 어미 조건을 붙인다. 부정 문맥(~아니라·~어도)은 정규식으로 못 잡으니 해당 규칙만 완화하는 편이 정직하다.

13. 지정가는 체결되지 않는데 현금·수량은 계속 잠근다 중간 코드확인

증상
reserve_order가 account.reserved_balance·holdings.reserved_quantity를 잠그는데, 정산기(orders/route.ts:112)는 order_status === "scheduled"만 본다. 지정가(pending)는 어느 경로로도 체결되지 않는다.
영향
"지정가 자동 체결 없음"은 이미 문서화된 범위(기능명세 §4)지만, 사용자 체감은 "돈이 사라졌다"다. 취소 버튼은 PortfolioScreen에만 있어 홈만 보는 사용자는 못 찾는다. 아이가 지정가로 전액을 걸면 그 세션 동안 아무것도 못 산다.
조치
홈의 지갑 줄에 잠긴 돈 n원 · 기다리는 주문 n건을 노출하고 탭하면 계좌로 보낸다. 코드보다 화면 문제다.

14. 지정가 예약의 reserved_amount와 limit_price × quantity가 무관하다 중간 코드확인

증상
POST /api/orders가 limit_price·reserved_amount·requested_quantity를 각각 독립적으로 받고 서로 대조하지 않는다. 호가단위 검사(isOnTick)는 하는데 금액 정합은 안 한다.
영향
지금은 지정가가 체결되지 않아(§13) 무해하다. 자동 체결을 붙이는 순간 결제 금액과 예약 금액이 어긋난다 — 기능을 켜는 PR이 이 결함을 상속한다.
조치
지금 고칠 필요는 없다. 지정가 체결을 구현하는 SPEC에 "접수 시 reserved_amount >= limit_price × quantity" 계약을 먼저 적어 둔다.

15. GET /api/orders가 쓰기를 한다 중간 코드확인

증상
조회가 정산을 겸한다(settleDueOrders를 먼저 돌림). 의도된 설계이고 settle_order가 멱등이라 중복 체결은 막히지만, 체결 시점을 브라우저 프리페치·크롤러·프리렌더가 정한다.
영향
사용자가 앱을 열지 않은 채 링크 미리보기만 떠도 예약이 확정될 수 있다. 데모 범위에서는 실질 피해가 없으나 "언제 체결됐나"를 설명할 수 없게 된다.
조치
남긴다. 대안(크론·엣지 함수)이 데모 인프라에 없고, 문서(기능명세 §6.4)가 이미 이 트레이드오프를 명시한다. 다만 심사에서 물으면 "의도했고 대안은 크론"이라고 답할 준비만 해 둔다.

18. 수량은 소수인데 realized_profit만 정수 반올림 낮음 코드확인

조치
남긴다. 실계좌로 갈 때 numeric으로 바꾼다.

Q. 서버가 클라이언트를 어디까지 믿나요?

답
"세 곳에서 믿고 있고 알고 있습니다 — 체결가·세션 폴백·예약일입니다. 지금 구조는 가족 안에서 서로 속일 이유가 없다는 데모 전제 위에 서 있고, 실서비스로 가면 체결가는 서버 시세로 덮고 DEMO_USER_ID 폴백은 프로덕션에서 잠급니다. 진짜 자산이 아니라 모의 지갑이라 지금은 위험 등급이 다릅니다."
왜
모른 채 넘어가면 "검증 안 했다"가 되고, 알고 남겨 뒀다고 하면 "범위를 정했다"가 된다. 우리 문서 관례([사실]/[추론]/[가정])와 같은 태도다.

Q. 시세 API가 죽으면 어떻게 되나요?

답
"토스 → 키움 → Supabase 보관 캔들 → 코드 픽스처 4단 폴백이 있어 화면은 죽지 않습니다. 대신 지금은 그게 대체 시세라는 걸 화면이 알려 주지 않는 것이 남은 과제이고, 배지 한 줄로 해결할 자리로 정리해 뒀습니다."
왜
폴백 사다리는 명백한 강점이다. 강점을 말하면서 그 강점의 그림자까지 같이 짚으면 "설계자"로 들린다.

Q. QA는 어떻게 했나요?

답
"자동 검증은 세 겹입니다 — npm test 242건, F10 안전 회귀 303건 + 분포 게이트, PR마다 CI. 여기에 사람이 도는 엣지 케이스 감사를 별도로 했고, 그 결과가 이 문서 19건입니다. 등급·재현 절차·소유 파일까지 붙여 두었고 치명 3건은 같은 뿌리(서버가 클라이언트를 믿는 자리)라 한 PR로 묶어 처리합니다."
왜
"버그가 없다"는 검증 안 한 팀의 말이다. 등급이 매겨진 목록을 내미는 것이 검증했다는 유일한 증거다. 이 문서 자체가 Appendix 후보 #13이다.
